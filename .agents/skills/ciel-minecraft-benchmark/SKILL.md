# Minecraft タスクを評価する

最初に [ベンチマークの仕様と実行手順](../../../docs/minecraft-benchmark-ja.md)を読む。課題を追加・性能を比較する場合は、同文書の「課題を追加する」「変更前後の性能を評価する」も読む。ローカル推論の設定変更時は [ローカル LLM](../../../docs/local-llm-ja.md)も確認する。以下のパス・コマンドの作業起点はリポジトリのルート。

## 環境とモードを選ぶ

- 実機試験は自宅サーバーの `~/work/ciel-companion-benchmark/server`、Compose プロジェクト `ciel-minecraft-benchmark` を使う。専用ワールドと `Ciel_Debug` で試し、本番・開発のサービスを試験のために再配布しない。Docker が必要なら起動してよいというユーザーの許可がある。
- `body` は LLM を呼ばず目的実行器と体を評価する。`conversation` は日本語の依頼から通常の pipeline を通し、既定でローカル LLM を使う。ローカルモードに OpenAI への自動フォールバックはない。LiveKit・Irodori は必要で、完全なオフライン試験ではない。
- 体・製作の変更はまず `body`、解釈・道具選択・プロンプトの変更は `conversation` を選ぶ。両方に影響する変更は両方を確認する。`needs_mind` は体だけで完結しなかった結果として扱う。
- RCON の採点器だけが初期化と採点を行う。識別印とリースの拒否を回避して続行しない。通常ワールドでの現場調査が必要なら [デバッグスキル](../../../.claude/skills/ciel-minecraft-debug/SKILL.md)に移る。

## 実行して原因を切り分ける

1. `scripts/server/benchmark-home.py inspect` で接続先を確認し、`stage` で手元の版を専用環境へ配置する。Python の選び方と完全なコマンドは仕様文書を参照する。
2. 対象課題を1配置・1回で試す。helper の `body` / `conversation --task <ID> --seconds 600` はスモーク試験であり、全課題評価ではない。全課題・複数配置・反復は配置先で `benchmark.run` の引数を指定する。
3. 合否はサーバー側の実状態で判断する。`report.json`、試行別 `result.json` と `trace.jsonl` を読み、初期条件、道具の失敗、目的状態、モデル要求を突き合わせる。会話の「できた」は成功の証拠にしない。
4. 環境障害と未達成を分ける。障害や `manifest.completion != complete` がある実行は比較を確定せず、原因を直して不足分を再実行する。残ったリースは実行中の runner が無いことを確認する `recover` を使う。
5. 結果を `pull` で取得してから、自分が起動した専用サービスを `stop` する。結果と専用ワールドは残す。

## 拡張と比較

- 課題追加は `server/benchmark/tasks.json` を起点に、必要なら `world.py` の復元・観測・採点、`run.py` の評価、`report.py` の集計、オフラインテストを一緒に更新する。新しい地形や到達条件は JSON の追加だけでは実装されない。
- 基準版と変更版で同じ課題・配置 seed・反復数・予算・キャッシュ条件を揃える。改善対象を明示し、モデル、プロンプト、体、評価器を同時に変えて効果を断定しない。
- 課題別の成功数/有効試行数、環境障害数、誤完了、停止、要求回数、到達時間を比較する。LLM の速度と体の実行品質を区別し、完了返答の観測も別に報告する。
- 失敗を再現できる課題を追加し、既存課題も再実行する。調整に使わない評価用の配置・依頼を別に確保する。仕様変更で比較条件が変わったら両版を同じ評価器で測り直す。

## 引き継ぐ情報

変更内容、モード、モデルとコードの識別情報、課題・seed・反復・予算、比較した結果の保存先、改善と悪化、未実施の範囲を日本語で報告する。単発の成功を性能基準と呼ばない。最新の実行状況と基準値は [基準測定](../../../docs/minecraft-benchmark-baseline-2026-11-09-ja.md)を読み、初版のスモーク試験と区別する。
