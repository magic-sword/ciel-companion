# 公式3モデルの構造解析：左右へ振る尻尾への応用

2026-10-16。ユーザーが `.local/reference-rigs/` に配置した公式配布データを読み取り専用で解析した。構造・キー・物理設定・モーションの詳細抽出は再生成できる中間データのため、Git対象外の `.local/reference-rig-analysis/analysis.json` に置く（再実行: `python -B scripts/live2d/analyze-tail-references.py`）。本書に設計に使った知見を残し、画像やモデル本体は複製しない。

## 結論

3モデルは、それぞれ「別素材の切り替え」「グループ単位の前後関係」「連続した曲がりと多段の揺れ」の詳細な参考になる。ただし、いずれも今回のサモエドの尻尾をそのまま実現した見本ではない。下記の実データで確認した事実と、シエル向けの設計提案を区別する。

## 名執 尽：差し替える素材を排他的なグループにする

対象：`natori_ja/natori_pro_t06.cmo3`、`runtime/natori.pose3.json`、`runtime/motions/mtn_00`〜`mtn_07.motion3.json`。基本モーション・表情用のCAN3も解析可能な形式であることを確認した。CAN3内の全タイムラインを評価したわけではなく、具体的な選択状態は書き出し済みモーションを根拠とする。

`natori.pose3.json` の排他グループは次のとおり。

| グループ | パーツID |
| --- | --- |
| 左腕 | `PartArmAL` / `PartArmCL` / `PartArmDL` |
| 右腕 | `PartArmAR` / `PartArmBR` / `PartArmER` |
| 時計 | `PartWatchA` / `PartWatchB` |

`FadeInTime` は **0.2秒**。8本の書き出しモーションの各グループは常に1種類を選択しており、そのモーション内の選択値は一定だった。例：`mtn_00` は左A・右A・時計A、`mtn_01` は左A・右E・時計A、`mtn_02` は左C・右A・時計A、`mtn_03` は左A・右B・時計B。

したがって、このデータは「一本のモーションの途中で自動的に腕が切り替わる」と解釈せず、**モーション側で選択状態を持ち、別の選択への切り替えをPoseのフェード設定で扱う構成**の参考にする。

CMO内では腕の種類ごとに専用の動作パラメーターがある。単一の腕画像を変形して全ポーズを作っているわけではない。前腕 `PartArmARFore` と `PartArmALFore` は描画順グループで、`ParamArmAR04` / `ParamArmAL04` のキー -1/0 により描画順400〜700を持つ。

シエルへの提案：左右用の素材を同一の選択制御で管理し、骨盤への接続と振りの位相を共有する。表示中は各素材を曲げ、隠れている区間で切り替える。0.2秒をそのまま使うのではなく、振る速さと遮蔽区間に合わせて切り替え時間を決める。見えている尾の二重フェードを避ける。

## ミアラ：一まとまりのパーツの描画順を制御する

対象：`miara_ja/miara_pro_t05.cmo3`、`runtime/miara_pro_t04.model3.json`、`runtime/motions/Scene3.motion3.json`。ネイティブとランタイムの版名がt05/t04で異なるため、モデル全体が同一だとは仮定していない。下記の描画順機能は実SDKでも確認した。

CMO内の `PartFairy` は描画順グループを有効にし、`ParamFairyDO` の -1/0/1 のキーで描画順 **100〜900**を持つ。`Scene3.motion3.json` も実際に `ParamFairyDO` を -1〜1 に動かすカーブを含む。単に名前だけの未使用パラメーターではない。

Cubism Coreへ実ランタイムをロードし、他のパラメーターを初期値にして次を確認した。`render_order` はCoreが計算した、そのモデル内の描画順序番号。

| `ParamFairyDO` | 妖精の `ArtMesh187` | 本体側の `ArtMesh100` | 相対関係 |
| --- | --- | --- | --- |
| -1 | 10 | 73 | 妖精が奥 |
| 0 | 183 | 59 | 妖精が手前 |
| 1 | 183 | 59 | 妖精が手前 |

生のアートメッシュの `draw_order` だけを見ず、グループを反映した `render_order` を確認する必要がある。表の結果は固定位置で描画順パラメーターを変えた検査であり、Scene3の再生や移動・物理演算を実行した結果ではない。

シエルへの提案：今回の尾を常に胴・袖・手の後ろに置くのであれば、**左右へ振るためだけに描画順を切り替える必要はない**。まず固定の背面描画と素材切り替えで作る。将来、尾を手前へ回す演出が必要になったときに、このグループ単位の制御を参考にする。描画順だけを変えても、尾が奥へ向く形そのものは作られない。

## 桃瀬ひよりPRO：連結した回転と多段物理

対象：`hiyori_ja/hiyori_pro/hiyori_pro_t11.cmo3` と同版のランタイム。FREE版も配置されていたが、本解析はPRO版を使用した。

CMOに `ArtMesh54_Skinning`、`ArtMesh55_Skinning`、`ArtMesh61_Skinning`、`ArtMesh62_Skinning` の4つのスキニング用パーツがある。それぞれ7つの回転デフォーマが親子に連結し、計28個の回転を持つ。例：`Rotation_1_ArtMesh55` → `Rotation_2_ArtMesh55` → … → `Rotation_7_ArtMesh55`。対応パラメーターのキーは -45/0/45。

物理設定 `PhysicsSetting10` と `PhysicsSetting11` はそれぞれ `ArtMesh54` / `ArtMesh55` の7パラメーターへ出力する。物理頂点は根元を含め11個あるが、出力先として使用する頂点番号は1〜7。**11個の物理頂点を、そのまま11個の描画上の関節と数えないこと。**

両グループの出力Scaleは根元側から **5 / 5 / 10 / 20 / 20 / 25 / 30**。入力は `ParamAngleX` / `ParamAngleZ` / `ParamBodyAngleX` / `ParamBodyAngleZ`。物理設定の数値だけで実際の遅れ時間や見た目を断定せず、連鎖と出力対応の見本として使う。

シエルへの提案：自分から振る動作の制御と、尾の中ほど・先端への物理出力を分ける。まず3段程度の試作から始め、必要な場合に段数を増やす。7段や上記Scaleをそのまま移植する必要はない。左右の表示切り替えで物理状態をリセットせず、共通の位相・揺れ状態を各素材へ対応させる。

## 次の試作仕様への反映案

1. 通常は尾が骨盤の後ろに向き、胴体に隠れる。隠れるために根元を横や上へ移動しない。
2. 左へ出る専用素材と右へ出る専用素材を用意する。各側の出入りから振り切りまでを、形の変化として作る。
3. 中央の切り替え区間で、毛先・下端まで本当に隠れているかを確認する。残るなら中央の奥向き素材を追加する。
4. 表示される素材を切り替えても、振る位相と毛先の追従は連続させる。
5. 遅い振り・速い振り・中央で停止・途中で逆転・上着なし・身体の傾きで、二重表示や飛びを調べる。

## 検査範囲と再実行

[解析スクリプト](../../../../../scripts/live2d/analyze-tail-references.py) はCMO3とCAN3のXML、ランタイムJSONを読む。Cubism Coreで3つのランタイムをロードし、物理出力先の全IDが実際のパラメーターとして存在することを確認する。ミアラでは描画順の前後反転も検証する。入力ファイル一式の処理前後のSHA-256を照合した。

Cubism Editorでの目視再生、CAN3全カーブの再生、Poseや物理演算の時間積分、シエルへの組み込みは行っていない。抽出された一部の日本語名には文字化けがあるため、照合はパーツ・パラメーターIDと参照関係を基準にした。

```powershell
& '.local\crown-completion-adoption\venv\Scripts\python.exe' -B scripts/live2d/analyze-tail-references.py
```
