# Minecraft タスクを評価する

最初に[ベンチマークの仕様・practical-v1・実行手順](../../../docs/games/minecraft/minecraft-benchmark-ja.md)を読む。課題追加・比較では仕様の該当章も読む。API容量や共有負荷を調べる場合は [共通GPU API](../../../docs/operations/shared-llm-api-ja.md)、推論の役目を切り替える場合は [ローカル LLM](../../../docs/operations/local-runtime-ja.md)を確認する。パス・コマンドの作業起点はリポジトリのルート。

音声認識精度・話し終わりから返答音声までの評価には[音声評価スキル](../ciel-voice-benchmark/SKILL.md)を使う。Minecraftの`conversation`は文字の依頼を送る評価であり、音声入力の精度・遅延の実測として報告しない。

## 環境とモードを選ぶ

既定はpractical-v1・配置11・1回、実行全体600秒。課題別の実用期限と、操作未発行・不進行・反復失敗による早期終了を使う。詳細な値は実用性評価の文書と `tasks.json` / `policy.py` を参照する。`--seconds` は短くする上限であり、期限を延ばす指定ではない。推論・共有先の待ち時間も利用者の待ち時間として評価する。

- 実機試験は自宅サーバーの `~/work/ciel-companion-benchmark/server`、Compose プロジェクト `ciel-minecraft-benchmark` を使う。専用ワールドと `Ciel_Debug` で試し、本番・開発のサービスを試験のために再配布しない。Docker が必要なら起動してよいというユーザーの許可がある。
- `body` は会話受付を省き、自然文の目的をMCP workへ渡してMindcraftと体を評価する。採集・製作には中核APIと共有ローカルLLMを使う。`conversation` は日本語の依頼から通常のpipelineを通す。両モードで共用GPU API（8094）を確認する。helperは追加のCPUモデルを起動しない。専用CPUモデルを調べる場合だけ `--llm-service dedicated` を明示し、別条件として報告する。OpenAIへの自動フォールバックはなく、会話評価にはLiveKit・Irodoriも必要。
- 通常は共有APIと他サービスを稼働させた状態を保つ。通常サービスの停止・API容量変更は、評価目的として必要な場合に範囲と影響を明示して行う。単なるベンチマーク実行から共有APIの再構成・負荷試験へ作業を広げない。共有先のCPU切替・容量不足を、専用CPUへの切替で隠さない。
- 体・製作の変更はまず `body`、解釈・道具選択・プロンプトの変更は `conversation` を選ぶ。両方に影響する変更は両方を確認する。`needs_mind` は体だけで完結しなかった結果として扱う。
- RCON の採点器だけが初期化と採点を行う。識別印とリースの拒否を回避して続行しない。通常ワールドでの現場調査が必要なら [デバッグスキル](../../../.claude/skills/ciel-minecraft-debug/SKILL.md)に移る。

## 実行して原因を切り分ける

1. `scripts/server/benchmark-home.py inspect` で接続先を確認する。会話評価では `scripts/server/shared-llm-home.py status` で共有APIのモード・準備状態・実容量を確認し、`stage` で評価する版を専用環境へ配置する。課題・評価器の変更では先に関連するオフラインテストを通す。Pythonの選び方と完全なコマンドは仕様文書を参照する。
2. 対象課題を `conversation --task <ID>` 等で1配置・1回だけ試す。CPUの遅さやAPIの待ち時間も実用上の時間に含め、失敗を避けるために期限を延ばさない。helperの単発実行は全課題評価ではない。不進行のまま全課題・反復へ進まない。
3. 合否はサーバー側の実状態で判断する。`report.json`、試行別 `result.json` と `trace.jsonl` を読み、初期条件、道具の失敗、目的状態、モデル要求を突き合わせる。会話の「できた」は成功の証拠にしない。
4. 環境障害・未達成・全体予算による中断・未実施を分ける。`budget_exhausted`・`stopped_early` の `skipped` は合否の分母へ混ぜず、全条件測定済みと扱わない。障害や未完了がある実行で全体比較を確定しない。残ったリースは実行中のrunnerが無いことを確認する `recover` を使う。
5. 結果を `pull` で取得してから、自分が起動した専用サービスを `stop` する。結果と専用ワールドは残す。

helperの既定は1課題・配置11・1回。`--all`と`--run-seconds`（最大3600秒）も使える。複数配置・反復は配置先の`benchmark.run`で指定する。大規模評価でも予定試行数と総時間予算を先に決める。早期停止を再起動の繰り返しで迂回したり、合格するまで再試行して結果を選んだりしない。同じ環境障害が再発したら、原因を変えない再起動を重ねず診断・修正へ戻る。修正後の補完は不足分と出典・キャッシュ区間を記録する。

## 結果を判定する

- `manifest.completion=complete` は予定した試行の終了で、全合格という意味ではない。終了コード0は全期待行動合格、1は課題失敗・打ち切り、2は環境障害。予定した課題・配置・反復と結果の対応を確認する。
- `skipped` は全体予算での中断・未実施。合否の分母から除外し、内訳と未測定範囲を示す。部分的な合格率を全課題の性能とは扱わない。
- `objectives_achieved` と `appropriate_stops` を分ける。材料のない専用課題の `outcome=appropriate_stop` は製作成功ではない。通常課題の断念は失敗。現在の不能条件oracleは、木材・所持品なしの石のつるはしだけを検証済み。報告の検出は保守的な日本語パターンなので、`decision_evidence` と動作停止の根拠も確認する。
- 道具名を本文に書いただけの返答、`game_call`、受付の `game_result`、完了の `game_task_result` を区別する。所持品が増えていないことだけから「操作なし」と断定しない。位置や所持品が変わらない待機と、実際の道具・推論の履歴を突き合わせる。
- `false_goal_done=0` や `completion_observed=true` は、自然文の完了報告が正確だった保証ではない。停止・不可能報告も、返答だけでなく未完了作業・位置・所持品・再開の有無で判断する。

## 拡張と比較

- 課題追加は `server/benchmark/tasks.json` を起点に、必要なら `world.py` の復元・観測・oracle、`policy.py` の進捗・終了判定、`run.py` の評価、`report.py` の集計を更新する。達成を求める課題か、不能時の報告・停止を求める課題かを明示し、各期限を実用性から定める。新しい地形や不能条件はJSONの宣言だけでは実装されない。
- 評価器の変更では、期待する成功・適切な断念に加え、誤った断念、動作中の報告、期限境界、全体打ち切りと未実施の記録をオフラインで確認する。既存の `test_minecraft_benchmark.py`・`test_benchmark_practical.py` を参照し、実機は必要な課題を単発から確認する。
- 基準版と変更版で同じ課題・配置seed・反復数・予算・キャッシュ条件を揃える。共有先の同時負荷・Irodori・歌によるGPU/CPU切替も記録する。`manifest.inference_server` は開始時の実容量・モードであり、試行中ずっとGPUだった保証ではない。改善対象を明示し、モデル、プロンプト、体、評価器を同時に変えて効果を断定しない。
- 課題別の成功数/有効試行数、環境障害数、誤完了、停止、要求回数、到達時間を比較する。LLM の速度と体の実行品質を区別し、完了返答の観測も別に報告する。
- 失敗を再現できる課題を追加し、既存課題も再実行する。調整に使わない評価用の配置・依頼を別に確保する。仕様変更で比較条件が変わったら両版を同じ評価器で測り直す。

## 引き継ぐ情報

### 再実行に必要なソースを残す

- 実行器・採点器・課題・テスト・依存定義・設定テンプレートをGitで管理する。再利用する補助処理は`scripts/server/`または`server/benchmark/`へ組み込み、実行方法を仕様へ反映する。`data/`や`.local/`の一時スクリプトを再実行の前提にしない。
- 追加したファイルは`git status --short`と`git ls-files -- <対象パス>`で追跡状況を確認する。表示されない場合は`git check-ignore -v -- <対象パス>`で除外を調べ、必要なソースを通常の追跡対象へ置く。結果領域を丸ごと強制追加して解決しない。ステージ済みとコミット済みを区別して報告し、ユーザーが依頼した場合は検証後にコミットする。
- 実設定・資格情報・ワールド・重み・結果・過去ソースのスナップショットはGit対象外。dirtyな版の再現に必要な差分と、外部データの指紋・保存先は結果と一緒に保持する。GitコミットとハッシュだけでGit対象外の内容まで復元できるとは扱わない。

### 測定の根拠を報告する

policy・モード・共有/専用・モデル/コード/source/suiteの識別情報、課題・seed・反復・実効期限・全体予算、打ち切り理由、結果の保存先、未測定範囲を日本語で報告する。通常のシエルと共有APIが稼働しているか、専用サービスの後片付けも確認する。生の結果はGit対象外なので、文書のコミットだけで保存されたと扱わない。

測定の条件・ソース・未確認範囲は[Minecraftの実測](../../../docs/testing/minecraft-results-ja.md)、現在の配布・確認範囲は[確認状況](../../../docs/testing/verification-status-ja.md)を参照する。現在の作業契約は[game-work-contract](../../../docs/games/game-work-contract-ja.md)。日付付き報告を増やさず、仕様と該当する実測資料を更新する。
