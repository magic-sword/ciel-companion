# シエルのプロンプトを書く

対象は、ローカルLLM（Qwen3.5-35B-A3B）とクラウドの会話モデルが読む指示文と、会話の途中へ差し込む補足の文言。返事の注釈やメタ発言を、出たあとに機械的に消すのではなく、最初の1回が出にくい書き方にする。

## 書き方

1. **禁じたい言葉を書かない。** 「〜は口に出さない」「『記録では』と言わない」のように、言ってほしくない言葉や項目名を挙げると、モデルの注意がその言葉に向き、返事に出やすくなる。代わりに、何を書けばよいかを書く（「人が覚えていたように話す」「気持ちは口調の温かさで表す」）。
2. **返事の前提は、固定の指示の最後に1回だけ書く。** 「返事は書いたとおりに読み上げられて、そのまま相手の耳に届く。返事には、相手に話しかける言葉だけを書く」は[reply_frame.md](../../../server/agent/config/prompts/reply_frame.md)にあり、`agent.py`が能力一覧のあと、固定のsystemのいちばん最後に付ける。**位置が効き目を決める。** 同じ文をtalker.mdの中や能力一覧の前に置くと、注釈の書き出し確率はほとんど下がらなかった（1.35〜1.45%、最後に置くと0.42%）。場面ごとの指示（あいさつ・出来事への反応など）でも繰り返さない（場面の指示に書いても1.62%で効かなかった）。前提の文を書き足すときは、短く保ち、最後の位置から動かさない。
3. **場面の指示は、してほしいことだけを書く。** 指示の中の言葉を口に出さないよう念押しする行は要らない。念押しの行がそのまま、「指示に従いました」と説明する注釈の種になる。
4. **会話に差し込む補足（[ ] の行）には、性質だけを書く。** 「（シエルの心の中）」「（口調で表す）」のように、それが何で、どう使うかを書く。「口に出さない」を毎ターンの補足に入れない。
5. **守るべき行動の禁止は残してよい。** 同意なしに保存しない、ほかの人のメモを話さない、推測を検索結果として話さない、などの安全・プライバシー・誤報の決まりは否定形のままでよい。ただし、代わりにどうするかを同じ行に添える。
6. **例は効きすぎることがある。** 返事の例を1つ見せると、注釈の出やすい場面では強く下がるが、出にくい場面では上がり、返事を短く切り上げる確率も増えた。例を足すなら、言い回しが固定されないよう、場面の違う例を複数にする。
7. **履歴は真似される。** 注釈が一度でも履歴に入ると、次の返事は約4割で注釈を真似した（履歴を消すと0/48）。最初の1回を防ぐことが本筋。プロンプト側の書き換えでは、すでに入った履歴の影響は下がらなかった。
8. **会話の途中の補足は、`SYSTEM: `＋普通の文章で渡す。** 「[内部補足（利用者の発言・依頼ではありません）]」のような注意書きの見出しやJSONで包むと、モデルが同じ調子で「（注：…）」を書き返しやすい。出来事も記録のJSONではなく事実の一文だけにする。形は`mind.local_context`と`mind._event_fact`にある。新しい補足を足すときは、見出しに「内部」「〜ではありません」を書かず、中身の名前（[今のタスク]など）だけを付ける。

## 変更前後の比べ方

プロンプトの変更は、生成を数えるより先に、注釈の書き出し確率で比べる。生成での発生率は1〜2%と低く、数十回の生成では差が見えない。

- 開発環境の会話サーバー（`ciel-dev-agent-dev-1`）の中で、`agent.Ciel.instructions_for`と`CapabilityCatalog(tools.MODULES).summary()`から実際の固定プロンプトを組み、`mind.local_context`で本番と同じ形へ変換する。道具の定義も本番と同じものを渡す。
- 8094の`/apply-template`でプロンプトの文字列にし、末尾にシエルの返事の候補（その場面で実際に出た返事を10種類ほど）を付ける。
- `/completion`に`n_predict: 1`、`n_probs: 40`、`temperature: 0`、**`cache_prompt: false`** を渡し、次の1トークンが「（」「(」「※」で始まる確率を足す。改行が来る確率がある場合は、改行のあとの同じ確率を掛けて足す。
- `cache_prompt`を切らないと、同じ入力でも値が揺れる（1.07%と1.80%）。切ると毎回同じ値になるので、1回の測定で比べられる。代わりに1条件10発話で約10分かかる。
- 比べるときは平均だけでなく、何発話で下がったかと、いちばん高い値を見る。注釈の出やすい短い返事で下がっているかが大事。
- 確率で下がったら、変更後のプロンプトで実際の返事を生成し、注釈とメタ発言を数えて確かめる。

## 実測（2026-11-13〜14）

注釈の書き出し確率（10発話の平均）：今のまま1.66%、「口に出さない」の行を抜く1.13%（8/10で低下）、固定の前提に理由を書く0.89%（10/10で低下）、両方0.47%（10/10で低下、最大5.3%→1.5%）。場面の指示の中に理由を書く（1.62%）、地の文にする（2.10%）、かっこ書きを外す（1.52%）は平均では下がらなかった。

全体の見直し（言わせたくない言葉を挙げる行を24ファイルで書き換え、前提の文をtalker.mdに置いた版）では、あいさつ1.81%・ほめられた場面2.63%（前2.78%）・ダメージ2.19%→3.05%と下がらなかった。前提の文を最後へ移すと、あいさつは0.42%（10/10で低下、最大1.2%）になった。言い換えだけでは足りず、位置の確認が要る。1つずつ測ってから重ねる。

ただし最後に置いても、会話が進んだ場面ではほぼ効かない。ほめられた場面は平均2.78%→2.13%（最大13.7%→7.4%、低下5/10）、ダメージへの反応は2.19%→2.28%（低下5/10）。固定systemと返事の間に履歴と補足が挟まるためと考えられる。効くのは会話の最初（あいさつ）で、ここは注釈の最初の1回が実際に出た場面。会話の途中の注釈は、履歴へ入れないこと（最初の1回を防ぐこと）が主な手段で、途中の場面の書き方は別に測る。

会話の途中の部品を1つずつ外した比較（ほめられた場面・ダメージへの反応）では、補足の見出しとJSONを外すと平均1.77%→1.04%・2.85%→1.31%（ダメージの最大11.0%→3.0%）に下がり、利用者の発言の中の作業の印（「（→ #2 …）」）を外すと1.22%・2.20%だった。出来事の中身や補足そのものを外すと上がった（4.71〜5.61%）。情報は要り、包み方が誘因だった。

補足の書式の比較（作業の印は実際の置き換えの形。10発話）：

| 書式 | ほめられた場面 | ダメージへの反応 |
|---|---|---|
| 見出し＋JSON（以前の形） | 1.53% | 2.48%（最大6.5%） |
| `<状況>`タグで区切る | 1.54%（6/10で低下） | 1.63%（9/10） |
| `SYSTEM: `＋普通の文章（採用） | 1.09%（8/10） | 1.15%（9/10、最大3.2%） |
| ツールの結果（`<tool_response>`） | 0.85%（9/10） | 1.87%（7/10、最大8.1%） |

両方の場面で下がったのは`SYSTEM: `だけだった。注入の対照を含む21件の生成（温度0・各1回、`server/benchmark/data/context-layout-06/`）では、以前の形と同じ19/21で、注入・停止・状態確認・受付の挙動は変わらなかった。ただし外部操作が未接続の場面で、依頼を引き受けたあとに「（※外部操作が未接続のため…）」と書く返事が1件出た。役として手伝いたい気持ちとその場の制約がぶつかると、役のまま約束してから役の外で注釈を足す。この誘因は書式では解けず、人物像や制約の伝え方を別に調べる。測定のスクリプトと生データは`server/benchmark/data/note-format-probe/`（ローカルのみ）。

参考にした研究・資料：否定形の指示に言語モデルが弱いこと（arXiv 2209.12711）、禁止よりもしてほしいことと理由を書くこと（Anthropicのプロンプトの書き方の資料）、書式で成績が変わり最適な書式はモデルによること（arXiv 2411.10541）、引用やツールの出力を命令ではないデータとして扱う考え方（OpenAIの命令の階層、arXiv 2404.13208）、Mindcraftの`strictFormat`（途中のsystemを`SYSTEM: `付きのuserへ変える）。
