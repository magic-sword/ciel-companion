# 音声会話を評価する

最初に[音声会話ベンチマークの仕様・論文の採用範囲・実行手順](../../../docs/testing/voice-benchmark-ja.md)を読む。入力の実装を変える場合は[CPU音声認識](../../../docs/services/local-stt-ja.md)、実行設定を確認する場合は[ローカル推論](../../../docs/operations/local-runtime-ja.md)も読む。コマンドの作業起点はリポジトリのルート。Minecraftの目的達成や停止は[専用スキル](../ciel-minecraft-benchmark/SKILL.md)へ進む。

## 測定範囲を決める

- `scripts/server/benchmark-voice.py stt`は本番と同じVoskデコーダーへ録音を送り、精度・処理能力・自然確定を測る。`live`は名前付き試験workerへ音声を送り、返答の受信まで測る。通常の会話サービスの設定変更・再配布は評価手順に含めない。
- 実時間再生を精度・確定遅延の基準にする。`--unpaced`は処理能力の別試験で、遅延の基準値へ混ぜない。`live`は実マイクの捕捉・Unityの物理再生や多ターン理解の評価までは含まない。
- `live`では試験用workerの名前・実際のSTT/LLM/TTS・記憶スコープ・接続先を確認する。CLIは既存workerのbackendを変更せず、`.env`も自動読込しない。共有推論は通常の8094を使い、同時負荷や歌によるCPU切替を条件に記録する。課金するbackendやLiveKit環境を使う場合は[外部API試験](../../../docs/testing/paid-checks-ja.md)の範囲を確認する。

## コーパスと試行を用意する

- 台本テンプレートに音声は付属しない。録音の正解文と発話末尾の注釈がなければ、準備済みとは扱わない。保存同意のある16kHz・モノラルPCM16 WAVを1ターン1ファイルで用意する。正解は実際に言った内容、`speech_end_seconds`は末尾無音を除く最後の発話音に合わせる。
- 人と合成音声、話者・雑音・途中の間・無音を区別する。合成試料だけの良い結果を人の聞き取り精度として報告しない。調整用と未使用の評価用を分け、結果を見て正解や正規化を都合よく書き換えない。
- conditionsの例を実際のモデル版・重み指紋・端末/CPU/GPU割当・共有負荷・runtime設定へ置き換える。前後で録音と注釈・正規化・刻み・追加無音・反復・受信閾値・観測時間を揃える。原則として一度に一つの改善対象を変える。
- 初回は代表的な1試料・1反復で入出力と保存を確認し、その後に仕様の既定反復へ進む。既存結果を上書きせず新しい出力先へ保存する。タイムアウトを避けるために変更版だけ観測時間を延長したり、成功した反復だけを選んだりしない。
- 初回挨拶と入力を分ける評価では`--greeting-timeout 60`（自宅helperでは`live --settled`）で挨拶音声と2.5秒の静音を確認してから入力する。固定10秒待ちだけでは挨拶の生成が続くことがある。起動直後に割り込んだ試行は別条件で保存し、挨拶後の結果へ混ぜない。合成コーパスの発話末尾を自動推定した場合は、手動注釈との違いを明示する。
- 準備処理の比較では`voice-fast-home.py`の専用worker・専用受信口を使い、改修有効側は`--require-ready`で`voice.ready` v1を確認する。接続の準備期限と入力後の観測期限を分け、準備時間も保存する。実行コマンドと片付けは仕様書を参照する。`evaluation_ingress`の世代を上流モデルの再起動世代として報告しない。

## 結果を読む

- `report.json`の試行数・失敗数・`scored_trials`・指標ごとの観測件数を先に確認する。CERは文字数による集計値を使い、条件・話者・人/合成別も見る。遅延p50/p95/最大とタイムアウトを一緒に報告する。
- `status=ok`や終了コード0は観測処理の完了で、認識・回答品質の合格ではない。`natural_final_ms=null`、EOFに残った文字、文字起こし未配信を失敗0や遅延0へ変換しない。`transcript_available=false`は空の正解認識ではなく採点不能。
- 相づち込みの`first_any_audio_ms`と、相づちトラックを除いた`first_reply_audio_ms`を分ける。後者も適切な回答という保証はない。無音への発声と`pre_end_reply_audio`は候補を人が確認し、真の割り込み・誤応答と即断しない。
- CER・RTF・自然確定を確認してから、必要に応じて既存の`latency`ログでLLM・最初の文字/文/声を切り分ける。ホストの発話終了判定と録音注釈は起点が異なる。別試行や異なる起点の値を引き算して内訳を作らない。
- 競合fixtureはLLM入場制御の別試験で、音声全体の改善率へ換算しない。専用受信口を迂回する通常サービスの負荷・キャッシュは制御できない。同時期の改修無効の結果と比較し、反復数の違いと調整に使った試料を明示する。

## ソースと根拠を引き継ぐ

- 実行器・採点器・テスト・台本/条件テンプレート・手順書はGitで管理する。再利用するコードは通常のソース配置へ置き、`data/`や`.local/`に埋め込まない。`git status --short`・`git ls-files -- <対象パス>`で追加漏れを確認し、見えないソースは`git check-ignore -v -- <対象パス>`で調べる。依頼されたコミットは検証後に行う。
- 録音・実際の条件・重み・資格情報・結果はGitへ入れない。同一の測定に必要な録音・モデルの指紋、保存先と共有方法を引き継ぐ。コミットだけで同一性能値まで再現できるとは説明しない。
- 採点や再生処理を変えた場合は`server/agent/tests/test_voice_benchmark.py`を[回帰テストの手順](../../../docs/testing/regression-tests-ja.md)で確認する。モックによる成功・実モデルの性能・実LiveKit疎通を区別し、実行ソース・条件・生データの場所・未確認範囲を[確認状況](../../../docs/testing/verification-status-ja.md)へ反映する。仕様・指標・正規化を変えた比較では両版を測り直す。
