# 長い目的をやり遂げる仕組み（調べたこと）

この文書は調査時点の記録。現在の採用方針は[設計方針の正本](design-policy-ja.md)、実装済みのゲーム契約は[作業契約](game-work-contract-ja.md)を参照。

状態：調べた（2026-11-07）。設計は [目的の係](goal-runner-design-ja.md)。前提は [マインクラフトで遊ぶ設計](minecraft-design-ja.md)（体）、[ゲームの知識の窓口](game-knowledge-design-ja.md)、[会話の組み立て（pipeline）の仕組み](conversation-pipeline-ja.md)（心）。

## 1. 何に困っているか

「石のつるはしを作って」のように、いくつもの段がある目的で、心が段を取りこぼす。2026-11-07 の例：

- 作業台を作るのに原木を使い、木のつるはしの材料が足りなくなった（「原木×1 が足りない」）。心は原木を集めずに、木のつるはしを 2 回続けて頼んだ。
- 「作り始めました」と言ったあと、体が断っても気づかずに話を続けることがある。
- 目的がどこまで進んだか（何ができて、何が残っているか）を、心は会話の流れからその都度思い出している。

今は心（LLM 1 回の返事）が、毎回「次に何をするか」を一から決めている。段が増えるほど、一度に正しく決めるのは難しい。目的を進める**ハーネス**（心の外で、計画・実行・確かめ・計画し直しを回す仕組み）が要る。

## 2. 参考になるもの

### 2.1 一般の仕組み

| 名前 | 中身 | シエルに使えるところ |
|---|---|---|
| **Anthropic「Building effective agents」**（2024-12） | ワークフロー（決まった道筋）とエージェント（LLM が道筋を決める）を分ける。型：prompt chaining・routing・parallelization・**orchestrator-workers**（中心の LLM が段を分けて渡す）・**evaluator-optimizer**（作る係と確かめる係を分ける）。「いちばん簡単な形から始め、良くなると示せたときだけ複雑にする」 | 目的の分解は orchestrator、段の実行は決まった道筋（ワークフロー）、できたかは別に確かめる |
| **Anthropic「Effective harnesses for long-running agents」**（2025-11） | 長い仕事を、何回かに分けて進める。初めに目的を**具体的な項目の一覧（JSON、各項目に `passes`）**へ広げ、毎回「進み具合の記録」と一覧を読んでから、**1 つずつ**進める。「できた」は会話の言葉ではなく、**確かめた結果**で決める。項目そのものは書き換えさせない | 目的の付箋に段の一覧を持たせ、段ごとに「できた」を体の様子（持ち物など）で確かめる。心には今の段と残りだけを渡す |
| **Google ADK 2.0**（Python は 2026-05 に GA） | 階層のエージェントから、**グラフのワークフロー**へ。エージェント・道具・関数を節（node）にし、分岐・並列・繰り返し・やり直し（`RetryConfig`）・**人に聞いて止まる（human-in-the-loop）**・止まったところからの再開を持つ。決まった流れと、コードで組む動的な流れの両方 | 「計画 → 実行 → 確かめる → 計画し直す」を節のグラフにする考え方。持ち主に聞いて待つ節。会話サーバーは LiveKit なので ADK をそのまま入れるより、考え方を借りる |
| **Claude Agent SDK / Claude Code** | 作業の一覧（todo。いつも 1 つだけ進行中）、計画だけを先に作って承認を受ける形、別の文脈で動く子のエージェント、道具の前後に差し込むフック | 「1 つだけ進行中」の一覧。シエルの付箋（board）に近い |

### 2.2 マイクラのエージェント研究

| 名前 | 中身 | シエルに使えるところ |
|---|---|---|
| **GITM（Ghost in the Minecraft、2023）** | 3 段：**Decomposer**（目的を、ネットの知識で部分目標に分ける）→ **Planner**（部分目標ごとに決まった形の行動の列を作り、うまくいった列を覚える）→ **Interface**（行動を操作にし、結果を返す）。ダイヤ取りが大きく上がった | 知識の窓口（search・facts）で分解し、体の技（決まった形の行動）で実行し、うまくいった計画を覚える |
| **DEPS（2023）** | Describe（何が起きたか）・Explain（なぜだめだったか）・Plan（計画し直す）・Select（次の部分目標を選ぶ）。**失敗したら、その理由を説明させてから計画を直す** | 体の「できなかった（理由・できたところ）」を受けて、計画し直す段を決まった流れで回す |
| **JARVIS-1（2023）**・**Optimus-1（2024）** | 計画の**記憶**（前にうまくいった計画を引いて使う）。Optimus-1 は知識のグラフで計画を導き、何も持たない状態から長い目的を進める | うまくいった計画を、ゲームの知識の窓口かシエルの記憶に残し、次に同じ目的で使う |
| **Plan4MC（2023）** | 技を「探す・扱う・作る」に分け、**技のつながり（グラフ）を前もって作り**、実行時はグラフを辿って技の列を決める。LLM は前もってのグラフ作りだけに使い、実行の失敗を減らす | 作り方の木（体の `planCraft`、facts の `from_scratch`）はもうある。「探す」の技（掘り下げる・探し歩く）が足りない |
| **Voyager（2023）** | 自分で課題を選び、技をコードで書いて確かめ、**技の書庫**に足していく | 技を作り足すのは「改造の依頼」（[ゲームの知識の窓口](game-knowledge-design-ja.md) の 7 章）として別に考える |
| **Mindcraft / MineCollab（2025）** | LLM が高い段の計画を作り、決まった技（47 個）で動く。段を詳しく伝え合うと、かえって成功が 15% 下がった | 心に細かい計画を毎回話させない。計画はハーネスが持つ |

### 2.3 ゲームで昔から使う計画の手法

- **HTN（階層的タスクネットワーク）**：目的を、決まった分け方で小さな仕事へ分けていく。**GOAP**（目的を目指す行動計画）：行動の「前提」と「結果」から、目的までの道を探す。**ビヘイビアツリー**：その場の反応を決まった木で選ぶ。
- 実際のゲームでは、**長い計画は計画器（HTN・GOAP）、その場の反応は木（BT）**と分けることが多い（AIIDE 2018 の HTN＋BT）。
- LLM と組むときは「**LLM を実行の流れの中に入れない**」のがよくある形：LLM は目的や行動に名前を付ける・計画し直しを始めるきっかけだけにし、実行は決まった仕組みが回す（Real Agents、LLM＋古典的計画器の研究 2025）。

## 3. シエルへの当てはめ（案）

調べたものに共通する形は、**分ける（計画）→ 1 つずつやる（実行）→ 結果で確かめる → だめなら理由を見て計画し直す**を、LLM の外の決まった流れで回すこと。シエルに当てはめると：

```
持ち主「石のつるはしを作って」／シエル自身の思いつき
   │
   ▼  心（LLM）：目的として受け取る（道具 start_goal）
目的の係（会話サーバー。ゲームを知らない、決まった流れ）
   1. 計画：ゲームの知識の窓口に「この物をどう作るか」を聞く（facts の from_scratch：集める物・作る段）。
      分からない目的（「家を建てる」など）は、心が search で調べて段に分ける（GITM の Decomposer）
   2. 段の一覧を目的の付箋に持つ（Anthropic の項目一覧。各段に「できた」の確かめ方：持ち物に何が何個あるか）
   3. 実行：今の段を 1 つだけ体の技で頼む（collect・craft …）
   4. 確かめる：体の様子（持ち物）で「できた」を決める。心の言葉では決めない
   5. だめなら：体の理由（足りない物・道具が無い・見えない・道が無い）で計画し直す（DEPS）。
      決まった直し方があればそれで（足りない物 → 集める段を前に足す）、無ければ心に理由を渡して考えさせる。
      同じ段で何度もだめなら、持ち主に聞いて待つ（human-in-the-loop）
   6. 終わったら：うまくいった段の列を覚える（JARVIS-1・GITM の記憶）
   │
   ▼  心と小脳：会話の後ろに「[今の目的]：石のつるはし（3/5：丸石を集めている）」だけを渡す。
      心は進み具合を話し、持ち主の「止めて」「先にこっち」で目的を止める・替える
```

- **ゲームを知らない形にする**：目的の係は会話サーバーに置き、計画の材料（作り方の木・知識）と実行（技）はゲームの側の窓口から受ける。ゲームが増えても同じ係で回せる。
- **当時の案はADK 2.0不採用**：既存pipelineに合わせて小さな実行器を自作する方針だった。現在の [シエルとMCPの再設計](minecraft-execution-redesign-ja.md)ではこの前提を見直し、ゲーム固有の計画をゲーム側へ分離する。ADK採用は最小実行例で比較して決める。
- **心の自発は残す**：目的を始めるのは、持ち主の頼みでも、シエル自身の思いつきでもよい（「頼まれていないことも、自分から」の方針）。ハーネスは「始めた目的を取りこぼさない」ためのもので、何をしたいかは心が決める。
- **今回の失敗に当てると**：「原木×1 が足りない」は、5 の決まった直し方（集める段を前に足す）で、心を通さずに直る。「作り始めました」と言ったあとの失敗は、4 で体の様子から決まるので、心が言い違えても目的の付箋は正しい。

## 4. 次にすること（案）

1. 目的の係の設計を書く（目的の付箋の形、段の確かめ方、計画し直しの決まり、心へ渡す文、ゲームの窓口に足す「計画の材料」の道具）。
2. マイクラで「物を作る」目的だけで試作する（facts の作り方の木で計画できる）。
3. 「探す」の技（掘り下げる・探し歩く）を体に足す（Plan4MC の Finding-skill。丸石が見えないときに止まった件）。
4. うまくいけば、作り方の木で決まらない目的（建てる・探検する）を、心と知識の窓口で分ける形へ広げる。

## 5. 小さな目標を重ねる（2026-11-07 に追加で調べた）

石のつるはしの途中で「作業台を置く場所が無い」と止まり、心は分かっていても次の手に進めなかった。失敗から小さな目標を作り、終わったら元の目標へ戻る仕組みを考えるため、深さの決め方とループの防ぎ方を調べた。

| 名前 | 中身 | シエルに使えるところ |
|---|---|---|
| **ADaPT（2023、NAACL 2024）** | まず実行し、**失敗したときだけ**その仕事を分ける（as-needed）。分けた子も失敗したら、さらに分ける。深さの上限 1〜3 で試し、**深いほど成功が上がった**（最大の伸びは 1 → 2、2 → 3 でも伸びる）。作り物のマイクラ（TextCraft）では上限 4 を与え、使った深さはレシピの深さに合わせて 1.9 → 2.8 に増えた | 失敗したときだけ小さな目標を作る。深さはレシピや状況に合わせて伸びてよい |
| **GITM（2023）** | 目的を知識で**部分目標の木**に分ける。Overworld の技術の木の物を全部取れた | 作り方で決まる部分（体の `planGoal`）は、深さに関係なく木として前もって分けられる |
| **BAR（ACL 2025 Findings）** | 目的の状態から**逆向きに**、再帰的に分ける（動的計画法のように）。状態の食い違いを確かめる部分と、段ごとの記憶を持つ | 作り方の木を逆向きに辿る今の `planGoal` と同じ考え方。深い物（ダイヤ）でも静的に計画できる |
| **Goal-Driven Autonomy（GDA、2010〜）** | 予想との**食い違いに気づく → なぜかを説明する → 新しい目標を作る → 目標を並べ替えて選ぶ（goal management）** の 4 つで回す。ゲーム（StarCraft）で使われた | 「作業台を置けない（食い違い）→ 穴の中で周りに空きが無い（説明）→ 場所を空ける・移る（新しい目標）」。目標の管理を係が持つ |
| **Infinite Agentic Loops（2026-07）** | 6,549 のエージェントの作りを調べ、止まる上限の無い繰り返しで実際に 68 件失敗していた。いちばん多いのは、失敗をそのままやり直す `while True` | 深さだけでは止まらない。**同じ物のやり直し・進まない状態**を見て止める上限が要る |

分かったこと：

- **深さを小さく決め打ちすると、複雑な目的ほど届かない**（ADaPT は深いほど成功が上がった）。ループは深さではなく、別の上限で止めるのがよい。
- 研究でよく使う止め方：**同じ目標が先祖にいたら作らない（輪の検出）**・**進んでいない（持ち物や場所が変わらない）なら止める**・**手数や時間の予算**・**同じ理由の失敗が続いたら人に聞く**。
- 分け方は 2 種類ある。**知識で決まる分け方**（作り方の木。LLM を使わず、深くても有限）と、**失敗から作る分け方**（ADaPT・GDA。心が状況を見て作る）。
