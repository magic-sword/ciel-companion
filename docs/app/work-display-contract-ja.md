# 作業・会話の表示契約

> 責務：goal.state/control v2、鮮度、表示対象を固定した操作と共通表示。

更新：2026-11-10。送信元、Unityの操作画面・配信映像・独立状態カード、ベンチマークを同じ契約へ移行済み。旧段一覧、pausedへの状態集約、作業を指定しない停止・再開は撤去した。ソースとオフライン検証の記録であり、本番配布の記録ではない。

## 表示する事実

Mindcraftの自然文依頼でもgoal.state/control v2を維持する。workのmessageに判断中・実行中を反映する。上流Agentの応答終了は目的達成を保証しないため、succeededの見出しは「処理終了」とし、本文へ「成果は未検証」とMindcraftの応答を表示する。evidenceのnative_finished=true・objective_verified=falseを、所持数や帰還の検証成功へ読み替えない。Unity側の文言変更も必要であり、旧アプリの「できた！」表示で検証済みと判断しない。

作業の正本はサービスのwork 1。シエルは計画・レシピ・修復手順を複製せず、依頼名、状態、サービスの説明、判断待ちの内容、残り実行予算を表示する。空の段一覧から0/0や進捗率を作らない。予算は完了予測ではない。サービスの状態を確認できない間は予算を表示しない。

| work.state | 表示 | 操作 |
|---|---|---|
| accepted | 受付済み・開始待ち | 止める |
| running | 実行中 | 止める |
| needs_decision | 判断待ち。サービスからの説明。体がオーナーに尋ねているとき（reason=owner_question）は、`decision_message`がその質問 | 止める／確認済みの判断に再試行する。質問への答えは会話で伝え、再試行は表示しない（`can_retry=false`） |
| cancelling | 停止確認中 | 再開・再試行を表示しない |
| succeeded | 処理終了。目的達成の確認範囲はサービスの説明に従う | なし |
| failed | 完了できませんでした | なし |
| cancelled | 停止を確認しました | なし |

終端は8秒間表示する。新しい作業を受け付けたら新しい作業を表示する。最後に確認した終端の事実は通信の鮮度が落ちても実行中へ戻さない。表示の形式不一致は終端の成功表示にも優先して状態不明にする。

作業と会話・リアクションは並行して示す。例：「石のツルハシ／実行中」と「会話：コメントへの返事を考えています」。発話中だから作業完了とは判断しない。独立配信カードには会話専用行を設け、依頼者の個人名・記憶内容・内部ログを載せない。長時間作業を伴わない機能選択・応答待ちも別に示す。`load_capabilities`等は利用者向けの機能名で表示する。直接の追従など、work以外の体の作業も会話とは別に表示する。

## 会話・自発判断の観測（activity.state v2）

2026-11-17のソース改修。送信・受信・操作画面の表示をv2へ揃えた。本番配布とOBSへの適用は未実施。配信の場面・座標・配置見本は[ciel-crafters-liveの画面設計](../../../ciel-crafters-live/docs/streams/minecraft/shared/layout-ja.md#状態と計画の表示を再設計する)を正本とする。

旧`background_thinking`は実処理から更新されておらず、旧画面の「裏の思考」は自発判断の実行状況を表していなかった。旧フィールドと`detail_version`を撤去し、`Initiative`と`ConversationDecision`の実行箇所から状態を投影する。現在の自発判断は`CIEL_INITIATIVE=1`が既定で、会話・出来事の変化と静かな時間を条件に動く。無条件の常時思考ではない。未採用の大きな状態機械の設計案と、現在の実行ループを混同しない。

| 行 | 表示する事実 | 例 |
|---|---|---|
| 会話 | 入力・発話・返答の生成と契機 | コメントへの返事、発話中 |
| 判断と実行 | 通常のsay/actループの実行段階と判断回数 | 判断、機能ロード、操作・結果待ち、結果確認、判断終了、取消、失敗 |
| 自発判断 | 有効性・待機理由・直近の結果 | 無効、会話優先、モード・歌・登録の条件待ち、静穏待ち、連続判断の抑制、新しい出来事待ち、判断中、今回は黙る |
| 体・作業 | body / goal.stateの確認済み状態 | 実行中、判断待ち、停止確認中、状態不明 |

通常の実行ループの固定構造は「入力待ち→判断→機能ロードまたは操作→結果確認→判断」で、判断から返答・終了へ分岐する。操作画面は共通表示ヘルパーで現在の節を強調する。これは進捗率や実際に通った全履歴ではなく、現在の実行箇所の投影である。ゲーム専用の受付判断は別経路のため、この通常ループの節へ推測で重ねない。ゲームの進行はworkとplanを表示する。自発判断の結果は発話・行動を選んだ事実であり、音声再生完了や作業成功の保証ではない。

`ciel.event`の`activity.state`は`v=2`、`stream_id`、送信ごとの`revision`、`valid_for_s=6`を持つ。状態変更時は250msでまとめ、変更がなくても2秒ごとに通知する。`mind`・`thinking_origin`・`calls`・`body`・`log`に加え、次の構造を送る。思考本文・モデルの理由文・個人の記憶を新規の状態項目へ含めない。

```json
{
  "initiative": {"phase": "waiting", "reason": "new_event", "outcome": "silent"},
  "decision": {"phase": "reviewing", "step": 2, "outcome": ""}
}
```

`initiative.phase`はdisabled / waiting / scheduled / deciding、`decision.phase`はidle / deciding / loading / calling / reviewing / finished / cancelled / failed。完了の内訳はnone / clarify / blocked / accepted / completeで、acceptedを作業成功にしない。失敗を「黙る」に変換しない。待機理由が同じままでもハートビートで鮮度を確認する。

未対応版・必須項目の欠落・不正な状態は未確認にし、v1へフォールバックしない。古いrevisionと退役streamは無視する。通知停止から6秒を超えたら現在位置・体の現在状態・経過秒数を現況として表示しない。新しい通知で復旧する。goal.stateの鮮度・終端保持は独立して判定し、会話の通知切れだけで確認済みの作業終了を書き換えない。

反映時は会話サーバーとUnityを一組で更新する。ソースの変更だけで配信済みとは扱わない。通常の配信カードは短い表示を維持し、詳細グラフは操作画面へ置く。OBS向けの独立した会話グラフ出力は画面設計に従う今後の実装であり、現時点で用意済みと扱わない。

## ciel.goalの状態通知

名前・topicは維持し、形式を **goal.state v2** に統一する。v1の変換・別名・二重送信は行わない。

```json
{
  "v": 2, "type": "goal.state", "stream_id": "会話内の送信元UUID", "revision": 12,
  "confirmed": true, "confirmed_ago_ms": 0, "valid_for_ms": 10000,
  "has_task": true,
  "task": {
    "session": "サービスのセッション", "task_id": "作業ID", "revision": 3,
    "service": "minecraft", "service_label": "Minecraft", "title": "石のツルハシを用意する",
    "state": "needs_decision", "message": "材料が見つかりません", "reason": "not_found",
    "remaining_known": true, "remaining_ms": 42000,
    "decision_id": "判断ID", "decision_message": "",
    "can_stop": true, "can_retry": true
  }
}
```

作業なしは `has_task=false, task=null`。UnityのJsonUtilityがnullを空オブジェクトとして復元する場合にも、has_taskから区別する。外側revisionは送信ごとの連番、task.revisionはサービスの状態版であり別物。同じ作業版の正常な状態取得も確認時刻を更新して通知し、完了・判断待ちの発話は重複させない。remaining_msだけは同じ作業版でも減る。体の計画が所要時間を示したときは、新しい作業版で増えることがある（作業契約の期限の延長）。

サービスの確認間隔は2秒、RPC期限は6秒、表示の確認有効期間は10秒。通信失敗は即座にconfirmed=falseとし、アプリだけ通信が途絶えた場合も受信時刻とconfirmed_ago_msから有効期間を判定する。状態変更時刻を接続確認の代用にしない。実行予算はサービスの残りとホストの固定期限の小さい方に制限する。判断・再送・復旧で期限を延ばさない。ホストの固定期限は、サービスが計画の見積もりで延ばした残りに合わせて延ばす（30分まで）。

実行中に確認が失効したら「状態不明・停止未確認」を表示し、最後の作業IDは保持する。同じ版の正常応答でも確認を復旧できる。古い外側revision、退役したstreamの通知は適用しない。不正な通知・未対応の版は状態不明にし、待機・成功・停止に置換しない。

### 計画グラフ

ゲームが計画を報告している作業では、`task.plan`に計画グラフ（[plan v1](../games/game-work-contract-ja.md#計画グラフplan-v1)）が付く。`goal.state v2`の任意の項目で、無いアプリは無視する。

- **計画グラフのウィンドウ：** 別ウィンドウ「CIEL Broadcast 計画グラフ」（配信版のWindowsだけ、OBSのウィンドウキャプチャ用）に全体を出す。
  - 列は依存の深さ、行は同じ深さの節。前提から線を引く。
  - 節の下に、その節で進めている段と選択（候補・選ばれた方法）を並べる。
  - 状態は色で区別する：実行中は青、選択待ちは橙、完了は緑、できなかったは赤。
  - 終わった子の段は、多いときは件数に畳む。
- **状態カード：** 計画の「いまの段」（選択待ちならその選択と候補）と、終わった最上位の節の数を、実行中の行として出す。
- **してはいけないこと：** 進捗率を作らない。見積もりは完了予測ではないと書き添える。
- **状態不明のとき：** 状態確認が切れた間は「最新の状態を確認できていません」とし、いまの段として見せない。
- **操作：** 送らない。計画の変更は言葉で頼む。

## 対象を固定した操作

```json
{
  "v": 2, "type": "goal.control", "action": "retry",
  "stream_id": "会話内の送信元UUID", "session": "サービスのセッション",
  "task_id": "作業ID", "revision": 3, "decision_id": "判断ID"
}
```

操作はstopまたはretry。Unityは表示中のスナップショットと最新状態のID・版・判断IDを照合する。ホストもロック取得後に再検証する。古い画面の操作を新しい作業に付け替えない。retryは確認が新鮮なneeds_decisionだけ。状態不明でも最後の作業を指定したstopは可能だが、送信しただけで停止済みと表示しない。cancellingからの再試行や終端への操作は表示しない。

## 実装と検証

送信と操作検証は`server/agent/goals.py`。Unityの受信と共通表示モデルは`CielConversation.Goal.cs`の`CielWorkPresentation`で、操作パネル・配信映像・独立カードが使用する。ベンチマークもtask.stateを参照し、RCONの実物による採点を維持する。

確認方法は[回帰テスト](../testing/regression-tests-ja.md)、実行済みの件数・描画・未確認範囲は[確認状況](../testing/verification-status-ja.md)に集約する。

## 反映時の単位

会話サーバーとUnityアプリを同じv2対応版として再ビルド・配布する。起動済みアプリも再起動し、会話を再接続する。旧アプリと新サーバーの混在を互換処理で隠さない。ゲーム側のwork 1は変更していないため、この表示変更だけでMinecraft本体・ワールドを再起動する必要はない。本番反映は確認済みGitコミット単位という運用を維持する。
