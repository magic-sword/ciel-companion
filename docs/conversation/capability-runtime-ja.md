# 能力カタログと会話専用MCPの契約

> 責務：能力カタログ、段階的な公開、呼び出し権限と実行管理。

更新：2026-11-10。[全体方針の正本](../project/design-policy-ja.md)に従う実装仕様です。

## 実装範囲

現在の標準構成 `CIEL_MODEL=pipeline`・`CIEL_VOICE=irodori` に適用します。Realtimeなどの旧会話構成は従来の公開方法です。Minecraftの外部MCP、作業契約 profile 2 / work 1、構造化受付と中止の処理は維持します。

| ID | サービス | 実行場所・境界 |
|---|---|---|
| 1 | game | `GameEnv`と作業クライアント経由で外部のゲームMCPを呼ぶ |
| 2 | karaoke | 会話専用MCPアダプター。捕捉・LiveKit制御はホスト、分析は既存singing HTTPサービス |
| 3 | memory | 会話専用MCPアダプター。意味単位の記憶処理は`memory_service.py`、本人確認・DBスコープは既存SpeakerBook/Store |
| 4 | research | 会話専用MCPアダプターとResearchService。検索・引用検証をサービス側、履歴・発話・画面への対応をホスト側で行う |
| 5 | minutes | 会話専用MCPアダプター。既存の議事録係を呼ぶ |
| 6 | conversation | 会話専用MCPアダプター。現在の会話履歴だけを検索 |
| 7 | thoughts | 会話専用MCPアダプター。内なる考えを参照・追加 |
| 8 | app | 会話専用MCPアダプターで検証し、AppEnvから既存の端末通信へ転送 |

基盤から呼ぶ検索・記憶更新・画像説明・YouTube取得も[共通のサービス境界](service-boundaries-ja.md)を使います。画像と配信の取得操作や記憶の保守操作は基盤専用で、LLMのサービス一覧を増やしていません。

会話専用アダプターはSDKのメモリtransportで実際のMCP初期化・`tools/call`・スキーマ検証を通します。呼び出しごとに接続を閉じるため、会話を越えたセッションや話者情報を共有しません。既存の道具処理とホストの状態に依存しており、独立起動可能なMCPサーバーへの分離は未実装です。この段階でHTTPポートやコンテナは増やしません。

## 入力イベントとの関係

能力のロードは道具・使い方の公開範囲を制御する。接続済みサービスからの重要な入力を受け取る条件にはしない。採用する入力側の設計は[サービス入力とリアクション](service-events-and-reactions-ja.md)を参照。標準pipeline向けの初版を実装済み。実機遅延と本番反映は未確認。

受信した通知から推論を起動しても、本人確認・コメントの権限・操作の所有権を引き継いで確認する。イベントを道具の呼び出し権限として扱わない。現在の操作単位のメモリtransportを、操作完了後の継続通知にも使えるとは扱わない。

## 公開と実行

1. `Mind.tools_for`が発言元、コメント権限、ゲームの所有状態、議事録への明示的依頼を確認します。
2. `CapabilityCatalog`がサービスの短いID・概要を作ります。名前の仮受付・本人の保存状態照会、停止・状態・現在時刻を、既存の発言元フィルターが許す範囲で個別公開します。探索の`load_capabilities`と実行の`execute_capability`も公開します。未分類の追加道具は公開しません。
3. LLMが`load_capabilities(service_ids=["3","4"])`などを呼ぶと、選択済みサービスを更新します。未知ID、重複、未接続・不許可サービス、4個以上の指定は一括拒否します。ここでは操作を実行しません。
4. ロード結果の`definitions`へ、対象の完全なschema、tool_id、version、ドメインの使い方を返します。会話末尾のtool結果に残し、`tools`や固定systemへ個別定義を追加しません。LRUで最大3サービスを保持し、失効した定義は再探索します。
5. LLMは取得済みのID・版と引数を`execute_capability`へ渡します。現在の許可、取得済みの版と正規定義、正規スキーマを確認し、既存の関数とMCPへ渡します。個別公開した道具はその関数を直接呼べます。名前や版を推測した呼び出しは拒否します。
6. `mind.only_given`は公開した入口以外を遮断します。`SessionMCP`はモデルへ見せる定義の集合とは別に`can_execute`で現在の実行許可を再検査し、各道具の本人確認・同意・状態検証も維持します。共通実行入口でも身体操作の対象名を解決し、一度の返答で複数の身体操作を通しません。

ロードは権限を昇格しません。コメントへ切り替わったら、読み込み済みの記憶サービスにも本人の記憶操作は公開されません。サービス一覧を表示することと、実行先の到達性が保証されることは別です。通信失敗を成功として扱いません。

通常会話も能力を利用できる共通の経路を使います。一般の挨拶に能力選択の別推論は追加せず、必要な場合だけモデルがロードします。詳細な本人登録・記憶操作の指示はmemoryのロードに合わせ、短い本人確認・同意・公開範囲の指示は常時保持します。議事録が稼働しておらず、その依頼もない場面では議事録状態照会を外し、無関係な質問で選択されるのを抑えます。ゲーム受付が処理した依頼をローダーで再実行しません。新しいゲームやアプリの道具は`bind_external`でサービスへ関連付けます。内部の道具を追加したら`tools.MODULES`、`FROM_COMMENTS`、カタログの所属を一緒に決めます。

## 結果と状態

内部MCPの構造化結果は`output`と`reply_required`を持ちます。歌の開始や記憶保存受付などの「返事を追加生成しない」指示も維持します。記憶の`queued`はバックグラウンド保存の受付を意味し、永続保存完了ではありません。

アダプターの返却はJSON表現16,000文字を上限とし、超過時は`status=truncated`・`clipped=true`と短縮内容を返します。元データの参照ID・出典・保持期間は各ドメインの既存契約を使います。汎用の全文保管・ページングサービスは未実装です。

内部の呼び出し全体には90秒の上限を設けます。これはLLM推論の制限時間やゲーム作業の期限ではありません。検索などの短い既存期限は維持します。取消はMCP処理にも伝播し、transportを閉じます。副作用発生後に取消や通信失敗が起きた場合は、成功・未実行を断言せずドメイン状態を確認します。

`service_call`で基盤専用処理を含む操作を記録し、`capability_exposure`で公開数・選択サービス、`capability_call`でサービス・道具・通信完了と所要時間を記録します。`transport_completed`は処理結果が返った意味で、作業成功ではありません。既存の`model_request`、`model_response`、使用量記録と突き合わせ、ロードによる推論回数の増加を含めて評価します。

## 検証と次の分離

併用方式を標準pipelineへ実装した。常時公開する2つは個々の操作であり、記憶サービス全体の探索・権限確認を省かない。発言元・接続状態・許可が同じなら、ロード前後で公開する定義と固定systemは同じ。許可が変わった場合はキャッシュ維持より実行制限の更新を優先する。サービス概要は登録済みの機能を示すもので、その発言での実行許可や接続先の正常性を保証しない。実機測定と反映状況は[確認状況](../testing/verification-status-ja.md)を参照する。

現行`mind.local_context`は複数のsystem情報を先頭へまとめるため、発言者・タスクなど動的な補足情報によるprefixの変化は残る。動的情報の信頼境界は維持し、能力ロードだけによる大きな先頭の変更を取り除く。初回挨拶前に実際の指示と個別入口・共通入口を含めて準備するが、全入力のキャッシュ再利用は保証しない。

個別ツールの段階的公開に加え、固定のdiscover/execute入口と、探索結果の末尾に完全なスキーマを追加する方式も評価器で比較する。サーバー側には正規スキーマを保持し、未知ID・未公開の道具・古い版・不正な引数を実行前に拒否する。これは通常pipelineへの反映ではなく、捕捉した合成状態を使う選択・検証の実験。固定入口の定義と過去の送信メッセージを不変にできても、モデル側のキャッシュ再利用を保証しない。新しい能力の追加と、既知の道具の再利用を分け、再探索・修正の回数や出力token増も比較する。

能力追加の入力短縮・事前準備・専門の道具選択指示は、[比較手順](../testing/voice-benchmark-ja.md#能力追加時の入力計算を比較する)の評価器内で試験する。通常pipelineの指示・権限制限はこの試験では変更しない。専用指示に切り替える候補も、動的な話者状態と会話・tool結果を保持する。事前準備の出力を実行せず、準備時間と本要求の時間を別に記録する。既に使えるキャッシュを毎回の準備で置き換えると遅くなる可能性があり、固定入力の事前計算を無条件に会話中へ追加する設計は採用しない。測定結果と未確認範囲は[確認状況](../testing/verification-status-ja.md)を参照する。

回帰テストは`test_capabilities.py`で、実際のMCP往復、SDKの引数注入、任意人物IDの拒否、同意未取得・本人不明、コメント権限、取消、返事の制御、結果上限を確認します。全体の実行手順は[回帰テスト](../testing/regression-tests-ja.md)を使います。

独立配備へ移す場合は、ホスト依存の音声・UI処理をコールバックや参照IDへ置き換え、認証済みの会話・話者・公開範囲をサービスへ引き渡す契約を先に定義します。生のRunContextをネットワークへ送信しません。共有DB資格情報や任意人物IDでホストの本人確認を迂回する経路は作りません。

評価は同じモデル・入力・共有GPU負荷で、従来の全道具公開と段階的公開を比較します。見るものは選択と実行の正確さ、初動までの時間、完了時間、推論回数、入力トークン、停止応答、ドメイン処理時間です。道具数の減少だけで高速化したとは判断しません。
