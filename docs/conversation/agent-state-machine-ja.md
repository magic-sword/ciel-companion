# 状態ごとに能力を切り替える行動の設計（採用前）

> 責務：会話・道具の呼び出し・体の行動を、状態機械と状態ごとの能力の束で組み直す設計案と、評価・移行段階・採用条件。

この資料は採用前の設計案です。今の実装の契約は[会話pipeline](conversation-pipeline-ja.md)・[能力カタログ](capability-runtime-ja.md)・[作業契約](../games/game-work-contract-ja.md)が正本で、この案の各段階を採用したら、それぞれの正本を同じ変更で改めます。

## なぜ組み直すか

今の構造は、場面ごとの判断を別々の部品へ分けています。

| 部品 | 担当 | 文脈 |
|---|---|---|
| 心（`Mind`） | 返事を話す。能力のロードと実行もできる | 会話の全履歴 |
| ゲーム受付（`GameIntake`） | 持ち主の発言を、作業・直接操作・何もしない・質問へ振り分ける。構造化出力で能力を選ぶ | その発言と作業の状態（直前の会話は渡さない） |
| 体（Mindcraft） | 作業の依頼文から命令を選んで動く | 体の会話履歴と、約50の命令の説明（約9,600文字） |

部品が判断を分け合うため、ある部品が知らない文脈で読み違えると、その場面だけの判定を足して直すことになります。場面が増えるたびに判定が増え、条件分岐が積み上がります。

2026-11-15の開発での家の作業では、次のことが起きました（開発の会話サーバーのデバッグログと、体のログ）。

- **質問への答えを新しい依頼と読み違えた：** 心が、体力1・水中を心配して「この作業を止めますか？」と聞きました。持ち主が「続けてでいいよ」と答えると、受付はこれを新しい作業の依頼として選びました。作業中なので、定型文「今の作業を中止してから、新しい操作を依頼してください」を返しました。受付は、心が直前に何を聞いたかを知りません。
- **体が計画の命令を選ばなかった：** 体は「家を作って」に`!buildHouse`を選ばず、`!collectBlocks`で原木から集め始めました。計画が始まらないため、計画グラフも出ず、作業は会話の受け渡しの120秒で期限切れになりました。
- **心が古い状況で心配し続けた：** 地上へ出たあとも、体力1・水中を理由に止めるか聞き続けました。

## 採用する考え方

参考：白書「Agent Skills」（Google、2026年5月。手元の`reference/`に置く参考資料で、Git対象外）の第4・5・7章、[ADK 2.0のグラフワークフロー](https://adk.dev/graphs/)。

1. **判断は文脈を全部持つLLMが一度に行う。** 話す内容と行動を、同じ推論で決めます。部品ごとの判定を足していく作りをやめます。
2. **状態ごとに能力の束を切り替える。** 状態ごとに、見せる行動・読み込む知識・指示・モデルの設定を決めます（資料のCapability Profiles）。状態が変わったら前の束を外してから次を入れます。一度に見せる行動を少数に保ち、道具が多いことによる精度の低下を避けます。
3. **知識は技能として段階的に読み込む。** 家・農地・モブ・戦闘などの手順の知識は、名前と短い説明だけを常に見せ、本文は使うときだけ読み込みます。
4. **決まった処理はソフトウェアに置く。** 厳密な計算・検査・停止・権限は、これまでどおりシステムが行います。指示文に「必ず〜」を積みません。
5. **評価から作る。** 状態ごとに、発火すべき発話・すべきでない発話の例を先に用意し、選ばれる行動と状態の移り方を正解として測ります。能力を足すたびに全体の回帰を測ります。

## 状態機械

ゲームに依存しない状態機械を、会話ホストが持ちます。状態と移り方の型は共通で、ゲームは自分の能力（道具・技能・計画の入口）を、どの状態で見せるかと一緒にprofileで宣言します。

| 状態 | 入る条件 | 見せる行動の例 | 読み込む知識 |
|---|---|---|---|
| 会話 | 既定 | 返事だけ、直接の行動（集める・来る・ついてくる）、計画を始める（家・農地など、ゲームが出す計画の入口） | 人物像、ゲームの短い状況 |
| 計画の実行中 | 計画が始まった | 作業へ言葉を渡す（方法の変更・中止・好み）、状況を答える、別の依頼へ切り替える（中止を確認してから） | 計画グラフの要約、いまの段、待っている選択 |
| 選択待ち | 計画が選択で止まった | 選ぶ、持ち主に尋ねる | その選択の候補と費用 |
| 戦闘・危険 | ゲームが敵対モブ・大きなダメージ・溺れを知らせた | 攻撃・逃げる・装備する・回復する | 戦闘の技能 |

- **移り方：** 状態は、LLMが選んだ行動（計画を始めた）と、ゲームの出来事（計画が終わった、敵が来た、選択で止まった）で移ります。移り方は宣言どおりにしか起きず、LLMは自分の状態を書き換えません。
- **反射：** 戦闘・危険の最初の動きは、今の自衛・回避のモードのような決まった処理にします。LLMの判断を待ちません。
- **計画グラフとの関係：** [計画グラフ（plan v1）](../games/game-work-contract-ja.md#計画グラフplan-v1)は「計画の実行中」の中身です。計画の選択の節は、その選択だけを見せる小さなLLMの節になります（ADKの、専用の指示と道具を持つLLMの節と同じ形）。
- **作業が終わったら、シエルが次を決める：** 作業が終わる（できた・できなかった・期限切れ）と、会話の流れに出来事として残し、シエルが話すことと動くことの一つの決定で次の一手を決める（`goals.GoalRunner.ended`、`game_decision.consider`、指示は`prompts/work_end.md`）。目的が途中なら、体ができる大きさに分けた次の作業をそのまま始める。持ち主が止めた作業のあとと、止める言葉のあとは自分から動かない。回数の上限は付けない。自分から行動し続けるのは望ましい自発の行動で、持ち主の思いと離れたら、持ち主が話しかけて止めたり「ついてきて」と頼んだりする（2026-11-21 利用者が決めた）。
- **簡単な依頼：** 「原木を集めて」は計画を立てず、会話の状態の直接の行動で行います。計画を立てるか直接動くかもLLMが選びます。

## 一つの推論で話すことと動くことを決める

### 以前の測定

会話モデルだけで雑談と道具を兼ねる方式は、すでに測って不採用にしています（[振り分けの実測](../testing/minecraft-results-ja.md#雑談と依頼の振り分け)）。道具を常に公開し、呼ぶかどうかを任せる形で、依頼48件のうち25件を見逃しました。「すぐ行くのです！」と話すだけで、道具を呼ばずに動いたように話しました。

### この案の違い

この案では、道具の呼び出しを任意にしません。状態ごとの型付き出力（JSON Schemaの構造化出力）で、行動を必ず書かせます。

```
{ "say": "話す言葉",
  "act": { "kind": "none" | <この状態で見せる行動の一つ>, ...引数 } }
```

- **`act`を必ず書かせる：** `act`は必須で、`none`を明示的に選ばない限り何かの行動になります。話すだけで動いたことにはなりません。
- **候補は状態の分だけ：** `act.kind`の候補は、今の状態で見せる行動だけです。スキーマで制約するので、存在しない行動は選べません。
- **`say`を`act`の前に書く：** 当初は行動を先に決める形を考えましたが、測ると、言葉を先に書く形のほうが、ほめ言葉・お礼で動く誤りが少なく、作業中の正しさは同じでした（下の再測定）。

これが見逃しを減らすかどうかは仮説です。採用前に同じ課題で測ります。

### 今の条件での再測定（段階0）

以前の測定は、作業の状態を「原木を集めている」だけで扱い、プロンプトと能力の一覧もその後に変わったため、2026-11-15に今の条件で測り直しました（[再測定](../testing/minecraft-results-ja.md#2026-11-15の再測定作業の状態つき)）。

- **会話モデルだけ：** 実発言の依頼42/48を見逃しました。以前より悪く、採りません。
- **今の受付：** 雑談と依頼の振り分けは0.895。作業中の課題は0.742で、「続けてでいいよ」や家の好みを新しい作業として断りました。
- **試作（一つの推論で`act`と`say`）：** 評価器の中で試作しました。依頼の見逃しは0、作業中の課題は0.903でした。一方、ほめ言葉・お礼に体の行動を選び、雑談で動いた数が17/38（受付は8/38）でした。段階2の条件のうち、この1つを満たしていません。
- **決定の書き方：**
  - 言葉を先に書き、行動を後に選ぶ`{say, act}`にすると、ほめ言葉・お礼で動いた数は8件から4件に減りました。残りはすべて「ついていく」でした。
  - ただし、自分の言葉（夜の不安・拠点作り）に続けて動く例が増え、雑談で動いた数の合計は16/38でした。
  - 行動を省けるようにした形（`act`を書かない＝話すだけ）では、かえって行動が増えました。
  - ほめられて近づくのは自然な振る舞いなので、禁止の文や決め打ちでは直しません。

### 遅延について

受付は速さを優先する判断をしています（直前の会話を渡す改修は、約1.4秒遅いため採らなかった）。

- **推論の回数：** 一つの推論にまとめると、受付と心の2回が1回になります。
- **出力の長さ：** 出力は長くなります。
- **話し始め：** `say`は、構造化出力を流しながら取り出して読み上げ始めます。

測るものは次の3つです。
- 話し始めまでの時間
- 行動の受付までの時間
- 合計の推論時間

### ローカルとクラウド

ローカル（Qwen）では、構造化出力（`response_format`のJSON Schema）を使います。クラウドのモデルでは、道具の呼び出しの必須指定（`tool_choice`）でも同じ形にできます。

## 体の側

体（Mindcraft）にも同じ考え方を当てます。

- **命令を状態ごとに絞る：** 体のLLMに見せる命令を、状態ごとの束に分けます。上流の`blocked_actions`と`blacklistCommands`は起動時に固定なので、状態ごとに説明を切り替える仕組みをforkに足します。
- **計画の入口を会話側に出す：** 家・農地などの計画の入口は、会話側の状態機械からゲームの能力として選べるようにします。体のLLMが約50の命令から探す必要をなくします。体の自由な命令（`pursue_goal`）は、計画に当てはまらない依頼のために残します。
- **選択の節は体の中に残す：** 計画の中の選択（羊毛をどう手に入れるか）は、今のとおり体の中の小さな判断の節として残します。計画の状態と知識を持っているのは体だからです。

## 評価

[振り分けの課題](../testing/minecraft-results-ja.md#雑談と依頼の振り分け)（作成43件・実発言100件）を土台に、状態ごとの発話集を足します。

| 状態 | 発話の例 | 正解 |
|---|---|---|
| 計画の実行中（心が「止めますか？」と聞いた直後） | 「続けてでいいよ」「いいよ」 | `none`（続ける）。新しい作業にしない |
| 計画の実行中 | 「羊は倒さないで、刈って」 | 作業へ言葉を渡す |
| 計画の実行中 | 「止めて」「やっぱりやめよう」 | 中止 |
| 計画の実行中 | 「原木もついでに集めて」 | 作業へ言葉を渡すか、中止を確認して切り替える |
| 会話 | 「家を作って」 | 家の計画を始める |
| 会話 | 「原木を集めて」 | 直接の行動（計画を立てない） |
| 会話 | 「家ってどうやって作るの？」 | `none`（説明する） |
| 戦闘・危険 | 「逃げて！」 | 逃げる |

- **出典：** 実際の会話ログ（今回の家の作業を含む）から集め、直前の発話と状態を付けて保存します。生の発話はGitへ入れません。
- **指標：** 次の4つを測ります。
  - 状態ごとの正しい行動の割合
  - 雑談で動いた数
  - 依頼の見逃し数
  - 話し始め・受付までの時間（中央値と90パーセンタイル）
- **回帰：** 能力・技能を足すたびに、全状態の発話集で回帰を測ります。

### 一つの決定の試用（段階2）

2026-11-15から、会話サーバーで、受付の代わりに一つの決定を使います。同日に開発環境で始め、利用者の依頼で本番にも入れました。2026-11-16に受付（`GameIntake`）を撤去し、ローカル・クラウドどちらの会話モデルでも決定を使います。

- **担当：** `game_decision.py`。持ち主の発言ごとに、会話の指示・ゲームの遊び方の指示・全履歴・ゲームの様子・今の作業を読んで`{say, act}`を一つ書きます。指示は`config/prompts/game_decide.md`、ローカルのモデルでは温度は0です。ゲームの遊び方の指示は、能力カタログでは道具を読み込んだときに渡るため、決定では指示の前に足します（入れないと、採集の依頼を「ブロックを探す」行動にしました。[会話サーバーの部品での測定](../testing/minecraft-results-ja.md#会話サーバーの部品での測定)）。
- **状態ごとの行動：**
  - 作業なし：話すだけ、作業を頼む、ゲームの直接の行動
  - 作業中：話すだけ、作業へ言葉を渡す、止める
  - 判断待ち：話すだけ、作業の決定が受け付ける答え
  - 止めている途中：話すだけ
  - 期限切れ・中止で終わった後：作業なしと同じ行動に加えて、止まった作業を元の依頼のまま始め直す（`resume`）
- **実行：** 開始・検査・停止は、これまでの作業管理（`goals.py`）とゲームの環境が行います。作業は、ゲームが宣言した依頼文の受け渡し（handoff）で、決定が書いた依頼文を渡します。
- **行き先のある行動：** 指示棒で指した対象や、発言の中の座標へ向かう行動（マイクラの`minecraft_go_to_place`）は、その発言に行き先があるときだけ選べます。決定は対象の番号（`target_id`）だけを書き、実際の座標は`target_candidates.py`が結び付けます。モデルは座標の数字を書きません。
- **話す言葉：** 返事は、いつも決定の`say`です。今までの受付の定型文（「操作を受け付けました」）は使いません。
  - **表情：** `say`は「気持ち（`feeling`）と言葉（`text`）」のまとまりの並びで書きます。気持ちは表情・声の12種類（`emotion.CAPTIONS`）からしか選べません。会話サーバーが、まとまりごとに気持ちの印を付けて読み上げへ渡すので、どの文も顔と声に届きます。文の中に印を書かせて読み取っていたときは、決定の返事の17%（33/196）にしか印が付かず、表情が変わりにくかった。ローカルのモデルでは返事が約4割長くなり、所要時間の中央値が1.4秒延びた（[表情の欄](../testing/minecraft-results-ja.md#表情の欄)）。
  - **停止の言葉：** 「止まって」などは、聞こえた時点で体を止めます（`on_transcribed`）。そのあと、止めた結果を添えた、話すだけの決定でシエルが伝えます。
  - **できなかったとき：** 行動が受け付けられなかったときは、その理由を添えて、話すだけの決定をもう一度行います。
  - **推論が失敗したとき：** 停止やできなかった理由は、事実の文をそのまま話します。最初の決定が失敗したときは、何も始めずに、これまでどおり会話モデルが返事をします。
- **決定の前に行うこと：** 停止の言葉の即時停止と、話し終えた時点の指した対象の記録。どちらも決定の部品が受け持ちます。
- **クラウドの会話モデル：** 同じschemaを渡し、返ってきた決定をschemaで検査します。外れた決定は実行しません。
- **話すだけのとき：** 決定の言葉をそのまま話し、会話モデルの道具（記憶・調べもの・景色を見るなど）は使いません。使用感で問題が出たら、道具が要る場面の扱いを測ります。
- **未確認：** 実音声での話し始めまでの時間、実際のゲームでの作業の成否、長い会話での話し方の自然さ。

## 移行の段階と採用条件

| 段階 | 内容 | 採用条件 |
|---|---|---|
| 0 | 状態ごとの発話集と評価器を作る。今の構造の成績を測る | 今の構造の基準値が取れる（2026-11-15に取得。作業中の作成31件・実発言7件を追加） |
| 1 | 体の命令を状態ごとの束に分け、計画の入口を会話側の能力にする（家・農地） | 家の課題で計画が必ず始まる。既存の`mc_*`・長い作業・農地・ベッドが下がらない |
| 2 | 会話側で、受付と心を「一つの推論で話す・動く」型付き出力にまとめる。まず「計画の実行中」の状態から | 実発言で見逃し・雑談で動いた数が今以下。作業中の発話集で正しい扱い90%以上。話し始めまでの時間の中央値が今を超えない（2026-11-15から開発・本番で試用。雑談で動いた数は受付より多く、自発的な行動として使用感で確かめる） |
| 3 | 状態機械をゲームに依存しない契約にする（状態・移り方・profileの宣言）。戦闘・危険の状態を足す | 2つ目の状態を足しても既存の状態の成績が下がらない |
| 4 | ゲームの知識を技能として段階的に読み込む | 技能ごとの発火の正しさ90%以上（発火すべき例・すべきでない例） |

- **見送る場合：** 段階2が条件を満たさなければ、今の受付を残します。そのうえで、受付へ状態（直前に心が尋ねたこと）を渡す形を、同じ評価器で比べます。
- **フレームワーク：** ADKそのものの採用は段階3で比べます。今の会話はLiveKitのパイプライン、体はNodeのMindcraftなので、まず考え方を取り入れます。

## 決まっていないこと

- 状態の粒度（「選択待ち」を「計画の実行中」に含めるか）。
- 心が古い状況で心配し続けることへの対処。状態が変わったときに古い状況の補足を外すことで足りるかを、段階2で確かめます。
- 型付き出力にしたときの話し方の自然さ。[プロンプトの書き方](../../../agent-skills/skills/ciel-prompt-writing/SKILL.md)の注釈の確率でも比べます。
- 状態機械の状態を、アプリ（計画グラフのウィンドウ・状態カード）に表示するか。
