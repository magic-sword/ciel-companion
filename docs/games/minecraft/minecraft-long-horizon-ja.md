# Minecraftの長い作業の計画

> 責務：Minecraftの長い作業を進めるための、依存関係のグラフ・計画グラフの実行器・LLMが判断する分岐と遅延した判断・世界の記憶・持ち主への相談の設計と、段階ごとの採用条件。

**状態：第1段・第2段を採用、第3段以降は設計案。** 第1段（依存関係の照会）と第2段（計画の実行器`!obtainItem`）を実装し、`mc_*`5課題が3回とも成功して第2段の採用条件を満たした（[第1段](../../testing/minecraft-results-ja.md#長い作業の計画-第1段依存関係の照会)・[第2段](../../testing/minecraft-results-ja.md#長い作業の計画-第2段計画の実行器)の実測）。実行器の現行仕様は[Minecraftサービス](minecraft-design-ja.md)へ移した。長い作業3課題でも、実行器ありの体は8/9、実行器を禁止した体は3/9だった（[比較](../../testing/minecraft-results-ja.md#計画の実行器の有無の比較長い作業と今の5課題)）。第2段は`item_goal.js`を土台にせず第1段の計画から作った直列の実行器で、方法の選択（保管場所・相談）と並行実行は第3段以降に残る。現在の判断の仕組みは[MindcraftのLLM通信と推論・行動ループ](mindcraft-agent-loop-ja.md)、体と接続の構成は[Minecraftサービス](minecraft-design-ja.md)、依頼・期限・判断待ち・取消は[作業契約](../game-work-contract-ja.md)、評価は[ベンチマーク](minecraft-benchmark-ja.md)が正本。本書の内容は、各段を採用した時点でそれらの正本へ移し、本書からは削る。

## 解決したいこと

Mindcraftは1回の推論で命令を1つ選び、結果を見て次を選ぶ。第1段で`!getCraftingPlan`は採掘道具・作業台・精錬を含む正しい手順を返すようになったが、その手順を1段ずつ実行するのもLLMに任されている。測定では、正しい計画を受け取った後も段を飛ばし、原木・板材・棒を作りすぎ、木のつるはしの前に素手で石を掘ろうとして期限に達した。`!craftRecipe`の回数を個数と取り違えて板材を使い切った回もある。

答えが決まっている手順の実行をLLMに任せていることが、仕組み（ハーネス）側の問題である。依存関係のグラフができていれば、順に実行するのはプログラムでよい。LLMが担うべきなのは次の判断である。

- 入手の方法の選択：作るか、保管場所から取りに行くか、持ち主に頼むか。
- 作れない・見つからない・失敗が続くときに、別の方法へ切り替えるか、相談するか、やめるか。
- 依頼の解釈：何を、いくつ、どこまで作るか。

人が行う次の手順は、部品はあるが今はつながっていない。

| 人の手順 | 現状 |
|---|---|
| 道具が無ければ材料から作る | 第1段で計画には入るが、実行はLLMの1手ずつの選択に任されている。上流NPCの[item_goal.js](../../../server/minecraft/src/vendor/mindcraft/src/agent/npc/item_goal.js)は入手方法の木をプログラムで実行できるが、LLMの命令からは使わない。 |
| チェストや拠点から取ってくる | `!takeFromChest`等は32ブロック以内の最も近いチェストだけ。中身の記憶は無い。`!rememberHere`の場所は、CIELが会話との接続ごとに作り直す`MemoryBank`で消える。 |
| 一時停止して持ち主に相談する | 作業契約に`needs_decision`と`minecraft_task_answer`はあるが、Mindcraftから入る口が無い。持ち主への発言は応答の終了として扱われる。 |

## 役割の分け方

| 担当 | 内容 |
|---|---|
| プログラム（計画グラフの実行器） | 依存関係のグラフを組み、着手できる節を順に実行し、実際の持ち物・ブロックで完了を確かめる。製作の回数の計算、道具・作業台・炉の用意、作りすぎの防止。決まった方法しかない節は判断を聞かない |
| LLM（Mindcraftの判断） | 依頼を目標（アイテムと数など）にして実行器を呼ぶ。方法が複数ある分岐での選択、失敗時の方針、相談するかどうか。行動の細部や順序は決めない |
| CIEL | 世界の記憶、資源を使ってよいかの権限、持ち主への相談、期限・取消・表示 |

上流の`item_goal.js`は、アイテムごとに入手方法（製作・採掘・精錬・狩り）の候補を持つAND/ORの木で、方法の選択を費用・深さ・失敗回数の計算で機械的に決め、着手できる節を`ItemGoal.executeNext`で1つずつ実行する。これを土台にし、(1)第1段の道具・作業台・精錬の扱いをそろえ、(2)方法の候補に「保管場所から取る」「持ち主に頼む」を加え、(3)費用だけで決められない分岐ではLLMに選ばせる。

## 依存関係のグラフ（知識）

アイテムを節とし、入手方法を辺とするAND/ORのグラフ。1つのアイテムの方法の候補はOR、1つの方法が必要とする材料・道具・設備はAND。ゲームの版のデータ（minecraft-data）から作り、LLMを使わず決定的に計算する。

| 入手方法 | 前提（AND） |
|---|---|
| 製作 | 材料、3×3なら作業台（所持または近くに設置済み） |
| 採掘 | ブロックの発見、採掘に必要な道具（丸石なら木のつるはし以上） |
| 精錬 | 原料、炉、燃料 |
| 保管場所から取る | 世界の記憶にある保管場所と在庫、使用の許可 |
| 持ち主に頼む | 相談への回答 |

目標から必要な部分グラフを取り出し、所持品と記憶にある在庫を差し引いて順に並べる。Optimus-1の階層的知識グラフ（HDKG）も、材料から作れる物への辺を持つグラフから部分グラフを取り出し、トポロジカルソートで材料と順序を決めて計画器へ渡す。

## 計画グラフの実行器

1つの作業の中で、選んだ方法で展開した小目標の有向非巡回グラフ（DAG）を持つ。各節は目標（アイテムと数など）、前提の節、状態（未着手・実行中・完了・失敗・判断待ち）、完了の根拠（実際の所持数・ブロック）を持つ。

1. LLMが目標を指定して実行器を呼ぶ（例：`!obtainItem("stone_pickaxe", 1)`）。
2. 実行器が部分グラフを組む。方法が1つに決まる節はそのまま展開する。
3. 前提がそろった節を、決まった命令（製作・採掘・精錬・移動）で実行する。回数は実行器が計算する。
4. 節の完了は実際の持ち物で確かめる。失敗したらその節と後ろだけを組み直す。
5. 判断が必要な分岐に来たら、LLMに選択肢を示して聞く（次節）。

VillagerAgentは、現在の状態から小目標の依存関係をDAGとして組み直し、状態管理部が環境と各エージェントの状態を追う（複数エージェントの協調が対象）。Plan4MCは技の依存関係のグラフを実行前に用意し、実行中はグラフの探索で技の順序を決めて、LLMの不安定さを実行時の判断から外している。本設計の実行器はこの2つと同じく、順序をプログラムで決める。

石のつるはしは「原木3→板材→作業台→棒→木のつるはし→丸石3→石のつるはし」がすべて方法1つの節なので、LLMの判断を挟まずに実行器だけで進む。

## LLMが判断する分岐と遅延した判断

### 判断を聞く分岐

- OR節で、候補の費用が大きく違う、または費用だけで比べられない（取りに行く距離と作る手間、他人の保管場所を使うかなど）。
- 候補がすべて使えない（材料が見つからない、道具が作れない）。
- 同じ節で失敗が続く（DEPSと同じく、失敗の結果と理由を示して方針を選ばせる）。
- 相談の条件に当たる（後述）。

費用が小さく1つに決まる分岐（どの木の原木を使うか、近くの採掘場所など）は実行器が既定の規則で決め、判断を聞かない。

### 遅延した判断

判断の分岐は、計画を組んだ時点ですべて決めない。実行器は次のように進める。

1. 判断が必要な分岐は「未決定」のまま計画グラフに置き、その分岐に依存しない節から実行を始める。
2. 未決定の分岐が近づいたら（着手できる節になる前、または数段先に見えた時点で）、LLMへの問い合わせを非同期に送る。中核APIの割り振り役は同時の要求を受け付け、判断の要求を優先する。
3. 答えを待つ間も、依存しない節の実行を続ける。答えが来たら、その分岐を選んだ方法で展開する。
4. 依存しない節が無くなっても答えが無ければ、作業の期限内で待つ。LLMが「持ち主に相談する」を選んだ場合は、作業契約の判断待ちへ進む。
5. 実行中に状況が変わったら（保管場所が空だった、材料が見つかった）、未完了の分岐だけを組み直して、必要なら聞き直す。

これは、必要になった時点で分解・計画するADaPT（As-Needed Decomposition and Planning）や、実行しながら計画を詰めるやり方に近い。計画全体を最初に決めないため、最初の操作までの時間を短くでき、状況の変化にも追従しやすい。

### LLMへの問い合わせの形

問い合わせはMindcraftの通常の判断ループの入力として送り、返答は命令（`!chooseMethod(...)`や`!askOwner(...)`等）で受ける。選択肢は実行器が作り、各候補に必要な前提・おおよその手間・使う資源・許可の要否を添える。LLMは候補から選ぶか、相談するか、作業をやめる。自由文の計画を書かせない。

## 世界の記憶と相談

- 世界の記憶：拠点・チェストの位置と最後に見た中身、覚えた場所を、ワールドの識別子ごとにCIELの記憶（中核API経由）へ保存する。会話との再接続で消さない。持ち主ごとの公開範囲を守る。実行器は「保管場所から取る」の候補をここから作る。
- 相談：LLMが`!askOwner`を選ぶと、体は作業を`needs_decision`にし、質問と選択肢をシエルが伝える。答えを観測としてMindcraftへ戻し、実行器が分岐を展開する。

相談する条件（聞く）：他人の保管場所の物を使う、拠点から遠くへ離れる、夜・溶岩などの危険がある、建物を壊すなど元に戻せない、入手方法が複数あって費用が大きく違う、立て直しても失敗が続く。聞かない：所持品と近くの資源で済む、すぐ元に戻せる、依頼の範囲内で費用が小さい。答えが期限内に来ない場合は、安全な既定（その場で待つ／作業を止めて理由を報告）にする。作業契約の期限・取消・回答の上限は変えない。

Mindcraftが命令を出さずに応答を終えたとき、実行器に未完了の節があれば、すぐ「処理終了」にせず、未完了の節と理由を示して1回だけ続行か相談かを聞く。

## 設計の原則

- 答えが決まっている手順はプログラムが実行する。LLMには方法の選択・相談・失敗時の方針だけを聞く。
- 判断プロンプトの文面を試験結果に合わせて書き換えない。新しい命令・照会と、その結果の文章を追加する。文面を変える場合は、変更前の失敗と使用感を報告してから決める。
- 実行器は上流の`item_goal.js`を土台にforkの`ciel`ブランチで拡張し、上流へ出せる一般的な形にする。CIEL独自のbrain・目標JSON・帰還ループは作らない。
- 世界の記憶、資源を使ってよいかの権限、持ち主への相談はCIEL側が持つ。
- 任意コードの生成・実行（`allow_insecure_coding`）は有効にしない。
- 作業の表示は[表示契約](../../app/work-display-contract-ja.md)のgoal.state/control v2を維持する。計画グラフの全節をアプリの段一覧として出す旧表示へ戻さない。

## 段階と採用条件

| 段階 | 内容 | 採用の条件（ベンチマーク） |
|---|---|---|
| 1. 依存関係の照会（実装済み） | 採掘道具・作業台・精錬を含む`!getCraftingPlan`、道具不足の失敗文 | 実行器の前提となる知識。単独では採用条件未達のため、2と合わせて判断する |
| 2. 計画グラフの実行器（採用済み） | 第1段の計画を順に実行する`!obtainItem`。方法が1つに決まる節だけをプログラムで実行し、判断の分岐は既定の規則 | `mc_crafting_stone_pickaxe`・`mc_crafting_wooden_pickaxe`が3回とも期限内に成功し、他の`mc_*`を下げない |
| 3. LLMが判断する分岐と遅延した判断 | 判断の分岐の問い合わせ、依存しない節の並行実行、失敗時の方針の選択、応答終了時の続行の確認 | 方法が複数ある課題で、LLMの選択に従って進み、待ち時間の間も依存しない節が進む。誤完了が減る |
| 4. 世界の記憶 | 保管場所と在庫、場所の記憶の永続化、方法「保管場所から取る」 | 近くに木が無くチェストにつるはしがある課題で、取りに行く |
| 5. 相談 | `!askOwner`と判断待ちの接続、聞く条件、期限切れの既定動作 | 会話モードで、相談が必要な場面で聞き、不要な場面で聞かない。回答に従って続く |

各段階で判断プロンプトの文面を変えずに済むかを確認し、変える必要がある場合は先に報告する。評価課題は、新しい能力ごとに「使うべき場面」と「使うべきでない場面」の対を用意する。上流Mindcraftの課題定義で表せない場面（チェスト・相談）はCIEL独自の課題にする。実行器を入れた後は、目的到達までの時間とモデル要求の回数も比べる。

## 参考にした手法

| 手法 | 取り入れること | 取り入れないこと |
|---|---|---|
| [Optimus-1](https://arxiv.org/abs/2408.03615)（NeurIPS 2024） | 依存関係の知識グラフから部分グラフを取り出し、トポロジカル順の計画を作る。実行中に計画が成り立つか見直す | 画像を含む経験の記憶と、その学習済みモデル |
| [VillagerAgent](https://arxiv.org/abs/2406.05720)（ACL Findings 2024） | 現在の状態から小目標のDAGを組み直し、状態管理で進み具合を追う | 複数エージェントへの割り当て（現在は1体） |
| [Plan4MC](https://arxiv.org/abs/2303.16563) | 技の依存関係のグラフを実行前に用意し、実行中の順序をグラフの探索で決める | 強化学習で学んだ技 |
| [ADaPT](https://arxiv.org/abs/2311.05772) | 必要になった時点で分解・計画し、実行と計画を交互に進める | 再帰的な分解をすべてLLMに任せること |
| [GITM](https://arxiv.org/abs/2305.17144) | レシピ等の文章知識で目標を小目標の木へ分解し、成功した計画を記憶する | キーボード・マウス操作への変換 |
| [DEPS](https://arxiv.org/abs/2302.01560) | 失敗した小目標の結果を説明させ、理由を踏まえて方針を選ばせる | 学習済みの小目標選択器 |
| [Voyager](https://arxiv.org/abs/2305.16291) | 成功した手順を説明付きで保存し再利用する、達成を別に確かめる | 任意のJavaScriptの生成・実行、自動カリキュラム |
| [JARVIS-1](https://arxiv.org/abs/2311.05997) | 似た状況で成功した計画を記憶から探して使う | 画像を含む記憶 |

いずれの論文も、持ち主に相談して資源の使い方を決める仕組みは主題にしていない。相談はCIELの作業契約と人格・記憶の側で設計する。論文の成功率は環境・行動単位・Minecraftの版・モデルが異なるため、本リポジトリの値と比較しない。

## 未決定のこと

- 実行器を呼ぶ命令の形：`!obtainItem`のような新命令にするか、`!goal`の目標文から実行器へ渡すか。
- 判断を聞く「費用の差」の基準と、数段先の分岐を先に聞くときの先読みの深さ。
- 「他人の物」の判定：チェストの所有者をどう決めるか（設置者の記録、持ち主の指定、拠点の範囲）。
- 世界の記憶の公開範囲：配信中や他の参加者がいるときに、拠点や在庫を発言してよいか。
- 相談の経路：音声・文字・アプリの選択肢のどれで聞くか、配信中の扱い。
- 計画グラフの要約をアプリへどこまで出すか（表示契約を変えない範囲）。
- 実行器・依存関係の照会を上流へ提案するか、forkに留めるか。
