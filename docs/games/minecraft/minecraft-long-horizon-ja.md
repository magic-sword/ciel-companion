# Minecraftの長い作業の計画

> 責務：Minecraftの長い作業を進めるための、依存関係のグラフ・作業の計画グラフ・世界の記憶・持ち主への相談・失敗からの立て直しの設計と、段階ごとの採用条件。

**状態：採用前の設計案。** 第1段（依存関係の照会）だけを実装し、採用条件の測定中。第2段以降は未実装。 現在の判断の仕組みは[MindcraftのLLM通信と推論・行動ループ](mindcraft-agent-loop-ja.md)、体と接続の構成は[Minecraftサービス](minecraft-design-ja.md)、依頼・期限・判断待ち・取消は[作業契約](../game-work-contract-ja.md)、評価は[ベンチマーク](minecraft-benchmark-ja.md)が正本。本書の内容は、各段を採用した時点でそれらの正本へ移し、本書からは削る。

## 解決したいこと

Mindcraftは1回の推論で命令を1つ選び、結果を見て次を選ぶ。作業全体の手順や、道具・作業台・材料の依存関係を先に解く仕組みは、LLMが使う経路にない。手順を考える助けは`!getCraftingPlan`だけで、採掘に必要な道具は含まない。

測定で確認した失敗（[Minecraftの実測](../../testing/minecraft-results-ja.md#木のつるはしの失敗調査と製作の修正)）：

- 石のつるはし：作業台まで作った後、つるはし無しで丸石の採集を3回繰り返し、「石を掘るには石のツルハシが必要、作るには石が必要」と堂々巡りした。先に木のつるはしを作る手順に至らない。
- 棒：原木が無いと分かると「木を伐採してきますね」と返して命令を出さずに応答処理を終える。作業は「処理終了」になる。

人が行う次の手順は、部品はあるが今はつながっていない。

| 人の手順 | 現状 |
|---|---|
| 道具が無ければ材料から作る | 依存関係はLLM任せ。上流NPCの[item_goal.js](../../../server/minecraft/src/vendor/mindcraft/src/agent/npc/item_goal.js)は採掘道具・作業台・炉と燃料を前提に含む木を組むが、LLMの命令からは使わない。 |
| チェストや拠点から取ってくる | `!takeFromChest`等は32ブロック以内の最も近いチェストだけ。中身の記憶は無い。`!rememberHere`の場所は、CIELが会話との接続ごとに作り直す`MemoryBank`で消える。 |
| 一時停止して持ち主に相談する | 作業契約に`needs_decision`と`minecraft_task_answer`はあるが、Mindcraftから入る口が無い。持ち主への発言は応答の終了として扱われる。 |

## 設計の原則

- Mindcraftの1手ずつの判断ループは残す。LLMに作業全体を一度に書かせない。依存関係の計算のように答えが決まる部分はグラフで計算し、LLMには次に取り組む節と命令の選択を任せる。
- 判断プロンプトの文面を試験結果に合わせて書き換えない。新しい照会・命令と、その結果の文章を追加する形にする。文面を変える場合は、変更前の失敗と使用感を報告してから決める。
- 世界の記憶、資源を使ってよいかの権限、持ち主への相談はCIEL側が持つ。Mindcraftは利用者として問い合わせる。
- 任意コードの生成・実行（`allow_insecure_coding`）は有効にしない。手順の再利用は、既存の命令の並びとして保存する。
- 作業の表示は[表示契約](../../app/work-display-contract-ja.md)のgoal.state/control v2を維持する。計画グラフの全節をアプリの段一覧として出す旧表示へ戻さない。

## 2つのグラフ

### 依存関係のグラフ（知識）

アイテムを節とし、入手方法を辺とする有向グラフ。ゲームの版のデータ（minecraft-data）から作り、LLMを使わず決定的に計算する。

| 入手方法 | 前提（辺） |
|---|---|
| 製作 | 材料、3×3なら作業台（所持または近くに設置済み） |
| 採掘 | ブロックの発見、採掘に必要な道具（丸石なら木のつるはし以上） |
| 精錬 | 原料、炉、燃料 |
| 保管場所から取る | 世界の記憶にある保管場所と在庫、使用の許可 |
| 持ち主に頼む・聞く | 相談（後述） |

目標のアイテムから必要な部分グラフを取り出し、所持品と記憶にある在庫を差し引いて、トポロジカル順に並べる。上流NPCの`item_goal.js`の木構造が土台になる。Optimus-1の階層的知識グラフ（HDKG）も、材料から作れる物への辺を持つグラフから部分グラフを取り出し、トポロジカルソートで材料と順序を決めて計画器へ渡す。これにより石のつるはしでは「原木→板材→棒・作業台→木のつるはし→丸石→石のつるはし」が計算で出る。

### 作業の計画グラフ（状態）

1つのworkの中で、依存関係のグラフから作った小目標を節とする有向非巡回グラフ（DAG）。各節は目標（アイテムと数、場所、建物の一部など）、前提の節、状態（未着手・実行中・完了・失敗・相談待ち）、完了の根拠（実際の所持数・ブロック）を持つ。前提が完了した節だけを「着手できる節」としてMindcraftへ示し、LLMはその中から選んで命令を出す。

VillagerAgentは、現在の状態から小目標の依存関係をDAGとして毎回組み直し、状態管理部が環境と各エージェントの状態を追う（複数エージェントの協調が対象）。本設計は1体の作業に同じ考え方を使い、失敗や状況の変化で該当する部分グラフだけを組み直す。

グラフで管理する利点：

- 堂々巡りを防ぐ。前提が未完了の節（木のつるはし無しの丸石）は着手できる節に出ない。
- 進み具合を節の完了数で数えられる。ベンチマークの中間到達と同じ単位で、部分達成度に使える。
- 立て直しの範囲を絞れる。失敗した節とその後ろだけを組み直す。
- 相談の理由を説明できる。「保管場所のつるはしを使う／木から作る」のように、どの節のどの方法で迷っているかを持ち主へ示せる。

計画グラフはゲーム側（体）が持ち、作業契約ではゲーム側が計画・実行・修復を担当する分担を変えない。CIELへは状態の要約と相談だけを返す。

## 構成要素

| 要素 | 置き場所 | 内容 |
|---|---|---|
| 依存関係の照会 | forkの`ciel`ブランチ（上流へ出せる一般的な変更） | `!getCraftingPlan`を採掘道具・精錬まで含む入手計画へ広げる、または新しい照会命令にする。結果は着手できる順の文章 |
| 計画グラフ | 体（`server/minecraft/src/mindcraft/`） | workごとに作り、Mindcraftの命令の結果と実際の持ち物で節の状態を更新する。着手できる節と失敗の要約を実行文脈へ加える |
| 世界の記憶 | CIELの記憶（中核API経由） | 拠点・チェストの位置と最後に見た中身、覚えた場所。ワールドの識別子ごとに保存し、会話との再接続で消さない。持ち主ごとの公開範囲を守る |
| 相談 | 体の命令＋作業契約の判断待ち | 「持ち主に聞く」命令で`needs_decision`にし、質問と選択肢をシエルが伝える。答えを観測としてMindcraftへ戻す |
| 立て直し | 体 | 同じ節の失敗が続いたら、失敗の理由と別の入手方法を示して部分グラフを組み直す（DEPSの説明→立て直し）。それでも進めなければ相談へ |
| 手順の記憶 | CIELの記憶 | 成功した節の命令の並びを、前提と結果付きで保存し、似た節の例として示す（Voyagerの技の図書館を、コードではなく命令列で） |

### 相談する条件

聞く：他人の保管場所の物を使う、拠点から遠くへ離れる、夜・溶岩などの危険がある、建物を壊すなど元に戻せない、入手方法が複数あって費用が大きく違う、同じ節で立て直しても失敗が続く。

聞かない：所持品と近くの資源で済む、すぐ元に戻せる、依頼の範囲内で費用が小さい。

答えが期限内に来ない場合は、安全な既定（その場で待つ／作業を止めて理由を報告）にする。作業契約の期限・取消・回答の上限は変えない。

### 応答の終了の扱い

Mindcraftが命令を出さずに応答を終えたとき、計画グラフに未完了の着手できる節があれば、すぐ「処理終了」にせず、計画グラフの状態を示して1回だけ続行を促す。続行しない、または「探しに行く」等の約束だけを返した場合は、未完了の節と理由を付けて終了する。回数の上限と、相談と続行のどちらを優先するかは実装時に決める。

## 段階と採用条件

| 段階 | 内容 | 採用の条件（ベンチマーク） |
|---|---|---|
| 1. 依存関係の照会 | 採掘道具・作業台・精錬を含む入手計画。製作・採掘の失敗文に不足している前提を添える | `mc_crafting_stone_pickaxe`が成功し、既存の`mc_*`5課題を下げない。複数回の反復で確認する |
| 2. 計画グラフ | workごとのDAG、着手できる節の提示、節単位の部分達成度、応答終了時の続行の確認 | 棒・石のつるはしの誤完了・堂々巡りが減る。節の完了数を部分達成度として記録できる |
| 3. 相談 | 「持ち主に聞く」命令と判断待ちの接続、聞く条件、期限切れの既定動作 | 会話モードで、相談が必要な場面で聞き、不要な場面で聞かない。回答に従って続く |
| 4. 世界の記憶 | 保管場所と在庫、場所の記憶の永続化、入手方法「保管場所から取る」 | 近くに木が無くチェストにつるはしがある課題で、取りに行く（許可が要る設定では相談する） |
| 5. 手順の記憶 | 成功した命令列の保存と再利用 | 同じ配置の反復で、2回目以降の時間・モデル要求が減り、失敗が増えない |

各段階で判断プロンプトの文面を変えずに済むかを確認し、変える必要がある場合は先に報告する。評価課題は、新しい能力ごとに「使うべき場面」と「使うべきでない場面」の対を用意する。上流Mindcraftの課題定義で表せない場面（チェスト・相談）はCIEL独自の課題にする。

## 参考にした手法

| 手法 | 取り入れること | 取り入れないこと |
|---|---|---|
| [Optimus-1](https://arxiv.org/abs/2408.03615)（NeurIPS 2024） | 依存関係の知識グラフから部分グラフを取り出し、トポロジカル順の計画を作る。実行中に計画が成り立つか見直す | 画像を含む経験の記憶と、その学習済みモデル |
| [VillagerAgent](https://arxiv.org/abs/2406.05720)（ACL Findings 2024） | 現在の状態から小目標のDAGを組み直し、状態管理で進み具合を追う | 複数エージェントへの割り当て（現在は1体） |
| [Plan4MC](https://arxiv.org/abs/2303.16563) | 技の依存関係のグラフを実行前に用意し、実行中はグラフの探索で技の順序を決める。LLMの不安定さを実行時の判断から外す | 強化学習で学んだ技 |
| [GITM](https://arxiv.org/abs/2305.17144) | レシピ等の文章知識で目標を小目標の木へ分解し、成功した計画を記憶する | キーボード・マウス操作への変換 |
| [DEPS](https://arxiv.org/abs/2302.01560) | 失敗した小目標の結果を説明させ、理由を踏まえて立て直す | 学習済みの小目標選択器 |
| [Voyager](https://arxiv.org/abs/2305.16291) | 成功した手順を説明付きで保存し、次の課題で探して組み合わせる。達成を別に確かめる | 任意のJavaScriptの生成・実行、自動カリキュラム |
| [JARVIS-1](https://arxiv.org/abs/2311.05997) | 似た状況で成功した計画を記憶から探して計画に使う | 画像を含む記憶 |

いずれの論文も、持ち主に相談して資源の使い方を決める仕組みは主題にしていない。相談はCIELの作業契約と人格・記憶の側で設計する。論文の成功率は環境・行動単位・Minecraftの版・モデルが異なるため、本リポジトリの値と比較しない。

## 未決定のこと

- 「他人の物」の判定：チェストの所有者をどう決めるか（設置者の記録、持ち主の指定、拠点の範囲）。
- 世界の記憶の公開範囲：配信中や他の参加者がいるときに、拠点や在庫を発言してよいか。
- 相談の経路：音声・文字・アプリの選択肢のどれで聞くか、配信中の扱い。
- 計画グラフの要約をアプリへどこまで出すか（表示契約を変えない範囲）。
- 依存関係の照会を上流へ提案するか、forkに留めるか。
