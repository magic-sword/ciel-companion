# ドキュメントの責務と管理

> 責務：資料の所有範囲、更新・統合・削除、リンク検証の管理ルール。

現在の資料は現在の仕様・手順・確認状況を表す。過去の設計や作業の経緯はGitの履歴へ置き、日付付きの報告書や旧仕様の折り畳みを現在のツリーへ増やさない。[資料一覧](../README.md)の表が全ファイルの担当範囲を定義する。

## 情報の正本

| 種類 | 所有者 | 書かないこと |
|---|---|---|
| 全体の判断 | design-policy | 詳細なプロトコル、配置コマンド、試験ログ |
| 構成の地図 | architecture | 旧構成図、各機能の全文仕様 |
| 機能・契約 | 各機能の正本 | 過去案、改修の時系列、別資料の設定表のコピー |
| 初期導入・運用 | development-setup / build / local-runtime | 測定結果や同意条件の独自定義 |
| テストの方法 | regression-tests / minecraft-benchmark等 | 毎回の実行結果の追記 |
| 現在確認できること・配布状況 | verification-status | 試行ごとの長い測定記録、未実施の成功扱い |
| 分野別の実測 | testingの各`*-results-ja.md` | 実行手順の複製、異なる条件の結果の合算 |
| 成果物の台帳 | assets配下のmanifestと隣接README | 過去の候補や版別フォルダ |

環境変数とComposeの設定ファイルはlocal-runtime、workのフィールドはgame-work-contract、UIへの状態はwork-display-contractが所有する。能力公開と入力イベント、workとbody、会話履歴と永続記憶を同じ資料へ混ぜない。利用者向け操作と内部の契約は、要約と参照でつなぐ。

## フォルダと共有スキル

配置先は[資料一覧のフォルダ担当表](../README.md#フォルダの担当範囲)に従う。`docs/`直下は索引だけにし、共通仕様は親分野、Minecraft・Live2D等の固有仕様は対応するサブフォルダへ置く。画像は`docs/assets/`、正式モデルの台帳は引き続き成果物に隣接して管理する。フォルダごとのREADMEや同じ仕様のコピーは増やさず、この一覧で役割を管理する。

文書の追加・統合・移動・削除、実装変更に伴う仕様更新には[ciel-documentation](../../.claude/skills/ciel-documentation/SKILL.md)を使う。共有手順の正本は`.claude/skills/<name>/SKILL.md`、Codexの同名の入口は`.agents/skills/<name>/SKILL.md`とする。文書管理もこの構成に従う。共通手順を両方へ複製せず、管理方針の変更もこの文書へ集約する。

## 更新する手順

1. 資料一覧から変更対象の所有者を探す。既存ファイルの該当節を更新し、毎回新しい設計書・日付付き記録・ADRを作らない。
2. 実装・設定・正式manifestに照合する。採用済み、実装済み、未実装、未確認、本番反映を区別し、別の場所の古い文を注記で残して併記しない。
3. 同じ情報を他資料が説明していたら、正本へ統合して参照へ変える。新しい別の責務が必要な場合だけファイルを分け、資料一覧へ役割を追加する。
4. 新しい測定は該当分野の実測資料を更新し、確認・配布範囲はverification-statusの該当項目を置き換える。日付・条件・ソース/モデル識別・データの場所・未確認範囲を保持し、古い詳細はGitから取得する。異なる版・条件の試験を一つの成功結果へ合成しない。
5. 削除や統合ではREADME、AGENTS、スキル、ソース内の文書参照も更新し、リンク検証を実行する。採用物や独自の制約を統合前に失わない。

設計判断の理由は、その機能の正本に現在必要な短い説明として残す。検討候補の列挙や研究メモを現行の仕様と並べず、採用する条件・未解決の課題へ整理する。外部製品の最新版・価格の羅列ではなく、このリポジトリが固定する版と根拠の所在を示す。

## 履歴と検証データ

`git log -- <path>`、`git show <commit>:<path>`で以前の内容を参照する。ファイルが削除されても過去のコミットから取得できる。履歴用のredirect文書、archiveディレクトリ、旧SVG構成図を残さない。

Git対象外の生の計測ログや音声は、Gitの履歴だけでは復元できない。必要な条件・指紋・保存先を分野別の実測資料へ残し、秘密・個人情報・重い成果物を文書整理のためにGitへ取り込まない。成果物のライセンス・保存同意・公開範囲も維持する。

ベンチマークの実行器・採点器・再利用する補助スクリプト、課題定義、テスト、依存定義、設定テンプレートはGitで管理する。`server/benchmark/data/`や`.local/`等の結果領域を再利用するコードの正本にしない。手順書には追跡するソースと別途準備する録音・重み・実設定を区別して記載し、同一条件の再測定に必要なデータは指紋と共有方法を明示する。

## 自動確認

```powershell
.\.venv\Scripts\python.exe -B -X utf8 scripts/docs/check-docs.py
```

正本一覧の収録漏れ、責務の記載、履歴用ファイルの混入、リポジトリ内のMarkdown参照先・見出しを確認する。外部リンクの内容や実装との意味的一致は自動では保証しない。Docsを更新しただけで新たな実機試験・配布を完了扱いにしない。
