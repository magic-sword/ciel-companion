# 会話の作り直しの成果（2026-10-29〜31）

ブランチ `refactor/one-log-one-mouth` で、シエルの「聞く・考える・話す」を作り直した。何が良くなったか、なぜそうしたかを、ここにまとめる。今の作りの地図（処理の順・部品・直す入口）は [会話の組み立て（pipeline）の仕組み](conversation-pipeline-ja.md)、細かい経緯と測定ごとの記録は [聞く・考える・話すの作り直し（設計）](attention-and-thinking-design-ja.md) の 5〜8 章にある。

## 1. 結論

- 本番の会話の組み立てを、Realtime（`CIEL_MODEL=realtime`）から **pipeline**（`CIEL_MODEL=pipeline`）に切り替える（2026-10-31、利用者が開発用で試して決めた）。Realtime の組み立ては残してあり、`server/compose.yaml` の `CIEL_MODEL` を戻せば元に戻る。
- pipeline は「1 つの音声検出 → 話している途中から文字が出る文字起こし → コードが振り分ける小脳と心 → Irodori の声」。返事の速さは Realtime とほぼ同じのまま、話の途中の頼みごと・会議での振る舞いが大きく良くなった。
- 料金は会話 1 回分で約 2 倍（下の表）。

## 2. 何が良くなったか（`bench_compare.py`、各 2 回）

### 途中でできたこと・外したもの

| 段階 | 結果 | 決めたこと |
|---|---|---|
| pipeline をそのまま作る | 会議は良くなったが、返事の声まで 3.3〜4.1 秒 | 毎回、全部の指示（約 1 万 6 千字）と道具 26 個を読ませていたのが原因 |
| 小脳と心に分ける | 小脳が一度も「考える番」を出さず、頼まれた議事録を始めなかった | 振り分けをモデルに任せず、コードで決める |
| コードで振り分ける・聞く係 | 長い話の途中の頼みが約 1.9 秒で通るようになった | — |
| 頼みを付箋で持つ | 「もうとっているのです」の言い間違いが消えた | 過去の発言を読み直して推し量るのをやめ、今の状態を 1 つの一覧で渡す |
| 道具を頼まれたときだけ渡す・頼みだけの発言に返さない | 心が勝手に議事録を終えることが無くなった（4 回中 0 回） | 指示文で止めるのではなく、道具そのものを渡さない |
| 待っている知らせを返事に含める | 「議事録、とり始めています。屋台を十個くらいに…」と、返事の中で伝わった | 知らせを別に言うのを待たせない |

## 3. なぜこうしたか

### 3.1 記録を 1 つ、口を 1 つ、判断を 1 か所に

作り直す前は、同じものが 2 つ・何か所にもあった。

- **会話の記録が 2 つ。** 共通の記録とは別に、Realtime も自分の会話を持っていた。そこへ話者・時刻・議事録の状態を差し込み、消えないように守る処理が 3 か所あった。pipeline では、返事のたびに共通の記録（`conversation.py`）から文脈を作る（`mind.py`）。
- **シエルを話させる入り口が 11 か所。** それぞれが今話してよいかを別々に決めていた。`mouth.py` の 1 か所に集め、なぜ話したかを記録する。
- **声の区切りを 2 つの仕組みが決めていた。** 手元の音声検出と Realtime の区切りが食い違い、返事が止まる・1 つ前の発言に答えるなどが起きていた。pipeline では音声検出を 1 つにした。

### 3.2 すぐ返す小脳と、必要なときだけ考える心

どの返事にも全部の指示を読ませると遅い。そこで、ふだんの返事は短い指示・道具なしの **小脳** が返し、次のときだけ全部の指示と道具を持つ **心** が返す。どちらにするかは **コード** が決める（`mind.py` の `route`）。

- 頼みごとの言葉がある
- 10 秒以上か 80 字以上話した
- シエルのあと 2 人以上が話した
- 会議（ひかえめ）のとき。黙るか答えるかは心が見極める
- 議事録などの知らせ・道具の結果の続き

モデル自身に「考えるべきか」を言わせる形も試したが、一度も言わなかったので、やめた。

### 3.3 話の途中の頼みを聞く係

Realtime では、相手が話し終えるまで返事のきっかけが無いので、長い話の途中の「議事録開始して」は約 16 秒後まで届かなかった。会議では名前を呼ばれないと届きもしなかった。

pipeline では、文字起こしが息つぎごとに届く。そこに「議事録・記録・まとめ」があれば、軽いモデルでシエルへの頼みかを確かめ、議事録をコードが直接始める（`listener.py`）。

### 3.4 頼みごとを付箋（タスク）で持つ

聞く係が始めた議事録の「議事録開始して」が、あとまで発言に残っていた。心はそれを読み直し、終了の頼みと取り違えたり、「もうとっている」と言ったりした。発言の文から今の状態を推し量っていたのが原因で、継ぎ足しの対処が 3 つ必要になっていた。

利用者の提案で、アプリが議事録や調べもののパネルを出すのと同じように、頼まれたこと・していることを状態を持った付箋にした（`board.py`）。

- 状態は「確認中 → 実行中 → 仕上げ中 → 完了／失敗」。
- 心・小脳・アプリが同じ 1 つの一覧を見る。
- 頼んだ発言は、送る会話の中で「（→ #1 会議の議事録をとる：実行中）」の印に置き換える。

継ぎ足しの 3 つは外した。

### 3.5 指示文ではなくコードで止める

指示文に書いても、モデルはときどき従わない。付箋で「実行中」と渡しても、心は「予算は去年と同じくらい」に議事録を終える道具を呼んだ。そこで、大事なところはコードで決める。

- 議事録を動かす道具は、今回の発言に頼みの言葉があるときだけ心に渡す。
- 頼みだけの発言（「あ、議事録開始して」）には返事を作らない。

### 3.6 知らせは話の切れ目か、次の返事の中で

議事録の知らせは、相手が 1.2 秒黙ってから言う（息つぎで言い出さない）。待っているあいだに次の知らせが来たら、最新の 1 つだけを言う。

相手への返事を作るときに待っている知らせがあれば、心がその返事の中で伝える。言い終えたら、知らせは別に言わない。

## 4. 残っていること

- **返事が消えることがある。** 長い話の場面で、返事が「シエル、」で一度止められた直後に、最後の質問への返事が声にならなかった（4 回のうち 2 回）。心の出力はあるが、声にも記録にもならない。原因を突き止めるには、作った文と道具の呼び出しをデバッグ用の会話ログに残す必要がある。
- **会議で人どうしの話に 1 回ほど口をはさむ。** 黙るかどうかの判断の問題で、付箋とは別に直す。
- 頭の 1 文字（「い」「屋」）で切れる返事がある。相手が話し続けて止められたもの。
- 料金は約 2 倍。文字起こし（`gpt-live-transcribe`）は分あたりの見積もりで、実際の請求とは照らし合わせていない。
- アプリは、付箋の一覧（`board.state`）をまだ表示しない。
- 調べもの・歌・声の登録は、まだ付箋に乗っていない。シエルの言いたいことを付箋にして満腹度を外すのも、これから（段階 3）。
