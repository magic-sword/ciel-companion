# 音声会話の構成の決定記録

日付：2026-10-12（日本時間）。仕様書 `docs/specification-ja.md` の 3・4・9 章を具体化したもの。

## 決めたこと

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 音声の中継 | **LiveKit Cloud**（開発中は無料枠） | 自宅サーバーは LiveKit Cloud へ外向きにつなぐだけで済み、ルーターのポート開放・ドメイン・TLS 証明書が要らない。外から自宅への入り口を開けない。モバイル回線でも安定する。接続先の URL とキーを変えるだけで、自宅の LiveKit サーバーへ移せる |
| 会話サーバー | 自宅の GPU サーバー（Ubuntu 22.04、RTX A2000 12GB、Docker）で `server/agent` を動かす | 運用費を抑える。外部へは LiveKit Cloud と OpenAI へ外向きにつなぐだけ |
| 会話モデル | OpenAI Realtime API（`gpt-realtime`）から始め、GPT-Live（`gpt-live-1`）と比べる | LiveKit Agents 1.8 の OpenAI プラグインが両方に対応（`CIEL_MODEL` で切り替え） |
| シエルの声 | Seed-VC で、OpenAI の声をシエルの声へ変換（フェーズ2） | OpenAI の音声会話の声は用意された声から選ぶ方式。抑揚・間は保ったまま声色だけ変えられる。Seed-VC は 10 秒程度の参照音声で使える。公式の値で遅延 約 0.43 秒（RTX 3060 ノート、変換 0.3＋機器 0.1） |
| 参照音声 | Irodori-TTS で合成したシエルの声（`D:\CIEL\企画設計\キャラ\シエル\ボイスサンプル`、リポジトリの外）。スタイルは設定資料 第7章 | 追加の参照音声も同じスタイルで作れる。Irodori-TTS のモデルの重みのライセンス（モデルカード）は公開前に確認する |
| GPU の共用 | 会話を試すときは、同じ GPU を使う vLLM（`gemma4-developer-agent-model-1`）を止める。止める前に毎回ユーザーに確認する | GPU のメモリ 12 GB のうち 11.8 GB を vLLM が使っている。Seed-VC は 2〜4 GB 要る |
| 遅延を減らす次の手 | 遅延が目標に届かなければ、Beatrice v2（変換 約 0.05 秒、CPU で動く。専用の学習が要る）を試す | 変換の部分は差し替えられる作りにする |

## 会話の記録

`AgentSession.start(record=False)`：LiveKit Cloud に会話の録音・文字起こし・ログを残さない（仕様書 8 章）。

## 接続の手順（開発）

1. LiveKit Cloud でプロジェクトを作り、Settings → Keys で URL・API キー・API シークレットを得る。Settings → Options で開発用トークンサーバー（Development token server）を有効にし、その ID を控える。
2. 自宅サーバーの `~/work/ciel-companion/server/agent/.env` に、`.env.example` をもとに LiveKit と OpenAI のキーを書く（利用者が書く。Git に入れない）。
3. リポジトリのルートで、Git Bash から `scripts/server/deploy-server.sh` を実行する。接続先は先に `scripts/server/.env.local` に書いておく（[ビルドとデプロイ](../build-ja.md#前提)）。`server/` 一式を送り、`~/work/ciel-companion/server` で `docker compose up -d --build` する（会話サーバー・読み上げ・DB。2026-10-15 に 1 つの `server/compose.yaml` にまとめた）。
4. Unity：`Assets/Settings/LiveKitTokenSource.asset`（Git 管理外）の Token Server Id に、1 の ID を入れる。`Assets/Scenes/Conversation.unity` を開いて再生する（メニュー CIEL ＞ Conversation ＞ Create Scene で作り直せる）。

開発用トークンサーバーは誰でもトークンを取れるので、開発中だけ使う。公開前に、認証つきのトークン発行（仕様書の `server/session-api/`）へ切り替える。

## OpenAI の独自の声（Custom voices）を使わない理由（2026-10-12 調査）

- 利用できるのは「対象の顧客」だけで、営業窓口への申し込みが要る（[Custom voices ガイド](https://developers.openai.com/api/docs/guides/custom-voices)）。
- 声の持ち主本人が決められた同意文を読んだ録音と、同じ人の声の見本（30 秒以内）が要る。Irodori-TTS で合成した声は「本人の同意」を用意できないので、この仕組みの対象外と判断した（合成音声で同意文を作ることは、同意の仕組みのすり抜けになるのでしない）。
- GPT-Live の独自の声は英語のアクセントのみと書かれている。日本語は未確認。
- 以上から、シエルの声は Seed-VC による変換で作る方針を続ける。

1 分の目安は、音声 1 分 = 入力 600 トークン・出力 1,200 トークン、会話の履歴のキャッシュが効く前提の第三者の試算（[forasoft](https://www.forasoft.com/blog/article/openai-realtime-api-pricing)）。

2026-10-31 から、本番は Realtime ではなく pipeline（`CIEL_MODEL=pipeline`。文字起こし → 小脳と心 → Irodori）で動かす（[会話の作り直しの成果](../conversation-improvements-2026-10-ja.md)）。以下は Realtime を使うときの方針。

方針：開発の既定は **gpt-realtime-2.1-mini**（安い）。会話の質を gpt-realtime-2.1 と比べ、GPT-Live は日本語と Seed-VC との相性を確かめてから判断する（`CIEL_MODEL`・`CIEL_REALTIME_MODEL` で切り替え）。

## 声質変換の測定（2026-10-13、自宅 GPU RTX A2000 12GB）

- 構成：Seed-VC のリアルタイム用モデル（xlsr tiny、`DiT_uvit_tat_xlsr_ema.pth`）、block 0.18 秒、拡散 8 ステップ、fp16。GPU のメモリは約 1.2 GB。
- 5.2 秒の音声を実時間で流して：処理の実時間比 0.33（間に合う）、変換による遅れ 約 0.19 秒（声の始まりを送ってから、変換した声の始まりが届くまで）。
- vLLM（gemma4-developer-agent-model-1）は、ユーザーの了承のうえ止めてある（しばらく止めたままでよい）。戻すときは `docker start gemma4-developer-agent-model-1`（GPU のメモリが足りなくなるので、声質変換サービスを止めてから）。

## 声の作り方の比較（2026-10-13）

ユーザーの評価：Seed-VC のリアルタイム用モデルは似ておらず、音が割れ・途切れる。高品質モデル（whisper-small）の一括変換・参照音声 16 秒は「かなり良い」。サンプルの量産とファインチューニングで上げられそう。
- 音割れは、変換後の音量が上限を超えて切り取られていたため（リアルタイムの出力の 0.35%）。実装の不具合。

Irodori-TTS（v4.1-Small、MIT）で直接読み上げる方法の速さ（自宅 GPU、参照音声 4 本 + 設定資料 7.1 のキャプション、`server/tts-irodori/bench_tts.py`）：

| 条件 | GPU | 6 字 | 13 字 | 33 字 |
| --- | --- | --- | --- | --- |
| bf16、40 ステップ（標準） | 1.7 GB | 0.66 秒 | 0.80 秒 | 1.22 秒 |
| bf16、16 ステップ | 1.7 GB | 0.44 秒 | 0.51 秒 | 0.72 秒 |
| fp32、40 ステップ | 3.4 GB | 1.48 秒 | 1.93 秒 | 3.59 秒 |

文を受け取ってから声が全部できるまでの時間。読み上げは文ごとなので、返事の出だしの遅れは「最初の文の文字が届くまで」＋「最初の文の合成」。

訂正：上の表は、同じ文を 2 回目に合成した時間だった。初めての長さの文は 1 秒ほど余計にかかっていた（Irodori-TTS が注意の計算に cuDNN を優先し、音声の長さが変わるたびに計算の準備をし直すため）。
読み上げサービス（`server/tts-irodori/server.py`）で EFFICIENT の計算に切り替えたところ、初めての文でも 16 ステップで **0.44〜0.72 秒**（6〜26 字）になった。

方針（2026-10-13）：ユーザーが 16 ステップの品質を標準の 40 ステップと聞き分けられなかったので、**Irodori-TTS（16 ステップ）で直接読み上げる方式**を既定にした（`CIEL_VOICE=irodori`）。会話モデルには文字だけを作らせる（音声の出力の料金もかからない）。Seed-VC の変換（`CIEL_VOICE=ciel`）は、サンプルの量産とファインチューニングで品質を上げる候補として残す。GPU を分け合うので、同時に動かすのはどちらか一方。

## 感情の印の崩れ（2026-10-16）

会話モデル（gpt-realtime-2.1-mini）が付ける文の頭の感情の印（`[happy]` など。`config/prompts/emotion.md`）が、合成した声の試験の数十文のうち 3 回ほど崩れた。かっこの無い「happy ところで」は、そのまま「happy」と読み上げられた。ほかに、一覧に無い「[happily]」、途中で切れた「[h]」があった（この 2 つは読み上げられず、感情が直前のままになった）。

| 案 | 判断 | 理由 |
|---|---|---|
| 印のまま、読み取りを強くする（`emotion.py` の `read_tags`） | **採用** | 遅れが増えず、文ごとに声と表情を変えられる。崩れ方は読み取りで拾える |
| 感情を道具（ツール呼び出し）で伝える | 採らない | 道具を呼ぶと返事がそこで止まりやすく、結果を返して作り直させる往復で 0.5〜1 秒ほど遅れる見込み（測ってはいない）。返事全体で 1 つの感情になりやすい。議事録の道具も、頼んだその返事では呼ばれないことがあり、このモデルの道具の扱いは安定していない |
| 印を 1 文字（`[h]` など）にする | 採らない | 長さは崩れの原因ではない（数トークンの差）。感情を言葉の意味で選べなくなり、頭文字がぶつかる（sad・surprised など）。崩れたときに元の感情を推し量れない |

読み取りで拾う崩れ方（`emotion.py`）：

- かっこの無い印：文の頭（返事の始め・改行・文の終わりのあと）にある感情の名前で、すぐ後が日本語のもの。その感情として読み、外す。「Happy birthday!」や文の途中の英語は外さない。
- かっこの中の空白や大文字（`[ Happy ]`）：その感情として読む。
- 一覧に無い印・途中で切れた印：一覧の名前と頭が合い（どちらかがもう一方の頭か、頭の 4 文字が同じ）、1 つに決まればその感情（happily → happy、h → happy）。決まらなければ（`[t]`）直前の感情のまま。どの場合も読み上げない。
- 返事に漏れた話者の 1 行（「[発言者：…]」、かっこが無いこともある）：外す。
- アプリへ送る文字起こしでも同じものを外す。文の頭の英字は、次の文字が届くまで持ち越して判断する。
- 確かめたこと：上の崩れ方と、崩れていない文・英語の文の 15 例（会話サーバーのイメージの Python で）。

## 返事の速さと相づち（2026-10-17）

利用者の困りごと：話しかけてから返事まで長く、聞こえたのかが分からない。言い直すと、作っていた返事が取り消されて作り直しになり、いつまでも答えないように見えた。

測り方：`server/agent/bench_latency.py`。本番とは別のコンテナで、`CIEL_AGENT_NAME=ciel-bench`・`CIEL_AGENT_PORT=8091` を付けた会話サーバーを動かし、その名前で呼んだ部屋にだけ入れる。試験用の参加者が、読み上げサービスで作った男性の声で 6 文（長い話・あいさつ・質問・「うん。」など）を話し、話し終わり（声の最後を送った時）からシエルの声が届くまでを測る。会話サーバーのログの「返事の速さ」に、会話モデルの側が発言を区切ってからの各段階の時間が出る（`latency.py`）。

| 区間（会話モデルの側が区切ってから） | 直す前 | 直したあと |
|---|---|---|
| 話し終わり → 区切り（semantic_vad） | 約 0.9 秒（ネットワークを含む） | 同じ |
| 区切り → 返事を頼む | 文字起こしを待つ 0.35 秒（短い発言はさらに 0.6 秒）＋話者の判定 0.1〜0.4 秒 | 0.25 秒（短い発言 0.35 秒）。待つあいだに話者の判定をすませる |
| 返事を頼む → 書き始め | 0.9〜1.5 秒（毎回 70 トークンほど考えていた） | 0.6〜0.9 秒（考える量を minimal） |
| 最初の文の読み上げ | 約 0.5 秒 | 同じ |
| **話し終わり → シエルの声（中央値）** | **3.3 秒** | 返事 約 2.5 秒。長い発言には **約 1.4 秒で相づち** |

決めたこと：

- **文字起こしを待たずに返事を頼む**（`turns.py`、ふつう・おしゃべりのとき）。会話モデルの側が区切ったら（speech_stopped）、0.25 秒だけ続きを話し始めないか見てから頼む。区切ったあとで続きを話し始めたら、頼んだ返事は会話モデルの側が取り消し、続きの区切りでもう一度頼む。大きな声がほとんど無い発言（物音かもしれない）だけは文字起こしを待つ。ひかえめのときは、呼ばれたかを文字起こしで見るので今までどおり待つ。
- **考える量を minimal にする**（`CIEL_REASONING`）。gpt-realtime-2.1-mini は既定で返事のたびに考えてから書き始めていた。minimal でも 20〜45 トークンは考える。会話の質は試験の範囲では変わらなかった（道具の呼び方への影響はまだ見ていない）。
- **相づち**（`aizuchi.py`）。返事を頼むのと同時に、会話の始めに読み上げておいた短い相づちを流す。質問（文字起こしが「？」「の」などで終わる）には「えっとね、」など、それ以外は「うん。」「うんうん。」など。文字起こしを 0.3 秒まで待ってから選ぶ（待たずに選ぶと、質問にも「うんうん」と返した）。短い発言・ひかえめ・タッチ・自分から話しかけるとき・あいさつには流さない。返事の最初の文の頭の同じような相づちは外して読み、返事は相づちが鳴り終わってから話す。
  - 相づちはシエルの声とは別のトラック（`ciel-aizuchi`）で送る。LiveKit の話す順番を通すと、相づちを流し終えるまで返事を頼めず約 0.5 秒遅れる。シエルの声のトラックの音源へ横から入れると、何回か流すうちに返事の声が途中から届かなくなった（相づちを止めると起きない）。アプリ（`CielConversation.cs`）は両方を鳴らし、口パクは大きいほうに合わせ、スピーカーを変えるときは両方の受信をいったん止める。
  - Irodori-TTS に長さを決めさせると、短い相づちは間延びした（「んー、」2.1 秒、「えっと、」1.7 秒、「うん、うん。」1.0 秒）。読み上げサービスに長さ（`seconds`）を渡せるようにし、相づちごとに長さを決めて読み上げる（「うん。」0.5 秒〜「うん、うん。」0.9 秒。`aizuchi.py` の `SECONDS`）。長さを渡すと、その長さちょうどの音声になった（CPU での試し）。念のため、前後の無音を除いて 1.2 秒を超えたら読み上げ直す（3 回まで）。
  - ただし考えるときの相づち（「えっと」「んっと」）は、短く長さを決めると考えているニュアンス（「えーっと……」）が消え、明るく短く返事をする声になった（利用者の評価）。書き方 4 通り（えっと・えーっと・んっと・んーっと）× 声の説明 3 通り（いまの相づち／言葉を探して語尾をのばす／首をかしげて考え込む）× 長さ 0.8・1.0 秒 × 2 回の 48 本を読み上げ、利用者が考えている雰囲気のものを 36 本選んだ（`server/agent/config/aizuchi/think/`）。読み上げは毎回少し違い、同じ指定でも語尾が途切れる・「ん」が高く元気な返事に聞こえるものがあるので、読み上げ直さずに選んだファイルをそのまま流す。
  - 利用者の評価：「えーっと」は全部使える（語尾が上がり、可愛らしく聞き返しながら健気に考える印象）。「えっと」は首をかしげて考え込む説明（C）が特に考えている雰囲気。それ以外（A・B）はシリアスでない場面なら違和感がない。「んーっと」は 0.8 秒が聞き返しながら考える、1.0 秒が深く考える印象。いまは、選んだものから同じ言葉が続かないように無作為に選ぶ（場面のシリアスさでは分けていない）。
- **話している途中の相づち**（2026-10-18、`turns.py` の `_watch_pauses`、`CIEL_NOD`）。利用者が長く話したとき、途中で相づちが無かった（それまでは話し終えたときだけ）。Realtime API には、話している途中に相づちを打つ働きはない。会話サーバーがマイクの声の大きさを見て息つぎを見つける：話し始めて（前の相づちから）3 秒たち、直前 3 秒の話し声より 20 dB 小さい音が 0.4 秒続いたら、聞いたときの相づち（「うん。」など）を流す。会話モデルの側がまだ区切っていないあいだだけ、ふつう・おしゃべりのときだけ、シエルが話していないときだけ。相づちから 2 秒以内に話し終えたら、返事の前の相づちは流さない（二重にしない）。
  - 試験（途中で 0.6 秒ずつ息つぎをしながら約 7 秒話す文など）：息つぎごとに約 3 秒おきに相づちが入り、どの発言にも返事をした。話し終わりの息つぎで打つと、話し終わりから約 0.4 秒で相づちが聞こえる。
  - 試験の参加者は声を鳴らさないので、相づちの声をマイクが拾う場合（エコー除去が効かないとき）は確かめていない。拾うと、会話モデルの側が相手の話の続きと受け取るおそれがある。
- 比べて採らなかったもの：話し終わりの判定を早くする（semantic_vad の eagerness を high、無音 0.5 秒の server_vad）。どちらも中央値が 2.5〜2.8 秒で、変わらなかった。

まだのこと：

- 実際のアプリでの聞こえ方（相づちの声の自然さ・かわいさ、毎回の相づちがうるさくないか）は、利用者に確かめてもらう。
- Android のスピーカーで、相づちの声をマイクが拾うと、作り始めた返事が取り消されるおそれがある（シエルの声を拾うときと同じ問題。エコー除去が効いていれば起きない）。起きたら `CIEL_AIZUCHI=0` で止められる。
- 短い発言（「おはよう」「うん」）は相づちを流さないので、約 2.5 秒かかる。アプリの側で、話しかけられたらうなずくなどの見た目の反応を足すとよい（未着手）。

### 続きを見る時間を短くする

区切りのあと続きを話し始めたのは 54 回中 13 回で、どれも 0.25 秒以内（最長 0.168 秒）だった。0.1 秒（短い発言 0.2 秒）と比べると：

### 考えている間の見た目

返事を頼んでから声が出るまで、アプリに「考えています…」と出し、声の波の棒に光の粒を流す（`CielConversation.Thinking`、`CielConversationUI`）。相づちの無い短い発言でも、聞こえたことが分かる。

- LiveKit Agents は会話サーバーの様子を参加者の属性 `lk.agent.state` で知らせるが、Realtime API と自前の読み上げの組み合わせでは thinking を通らず、listening から speaking へ直接変わった（15 回の返事すべて）。そこで会話サーバー（`turns.py` の `_set_thinking`）が、返事を頼んだときに `{"type": "agent.thinking", "on": true}`、続きを話し始めて返事が取り消されるときに `on: false` を送る（topic `ciel.event`）。
- アプリは、`lk.agent.state` が speaking になる（声が出る）か、`on: false` か、6 秒たつまで出す。
- 実機での見え方は、アプリを作り直してから確かめる。

## 話の中断（2026-10-22）

利用者の困りごと：シエルが話している途中に、咳やちょっとした物音で何度も話が止まり、会話にならないことがある。

原因：話し始めの判定は会話モデルの側（Realtime API の `semantic_vad`）。LiveKit は、その「話し始めた」（`input_speech_started`）を受けた瞬間にシエルの声を止める。LiveKit の「0.5 秒以上話したら中断」「物音だったら再開」「相づちを見分ける機械学習」は、会話モデルの側が話し始めを判定する作りでは使われない（LiveKit 1.8.3 の `AgentActivity._interrupt_by_audio_activity` は、その場合すぐ戻る）。この作りでは中断を無くす設定もできない（`allow_interruptions` を False にするとエラー）。会話モデルの側にも、話し始めで返事を取り消す設定（`interrupt_response`）がある。

再現（`server/agent/bench_interrupt.py`。シエルに長めに話してもらい、話し始めて 2.5 秒で音を入れる。開発用の会話サーバー、各 2 回）：

| 入れた音 | 直す前 | 直したあと（0.6 秒） | 直したあと（0.8 秒） |
|---|---|---|---|
| 雑音・声の入っていない咳のような音 | 話し続けた | 話し続けた | 話し続けた |
| 声の入った咳「ゴホッ、ゴホッ」 | **止まった** | 話し続けた（声 0.58〜0.62 秒。しきい値すれすれ） | 話し続けた（声 0.66 秒） |
| 「あっ」 | **止まった** | 話し続けた（声 0.24〜0.26 秒） | 話し続けた（0.22 秒） |
| 相づち「うん」 | **止まった** | 話し続けた（声 0.26〜0.28 秒） | 話し続けた（0.32 秒） |
| 本当の割り込み「ちょっと待って、シエル」 | 止まった（割り込みのあと 0.5〜1.0 秒） | 止まった（1.3〜2.0 秒） | 止まった（1.9〜2.1 秒） |

直す前は、止まったあとにその音（咳・「うん」）へ返事もしていた。

決めたこと（案A。利用者の判断）：話し始めの判定は会話モデルの側のまま、止めるかだけをこちらで決める（`interruptions.py`）。

- LiveKit が「話し始めた」を受ける処理を差し替える。シエルが話していないときは今までどおり。話しているときは、利用者の状態の更新は LiveKit に任せ、声は止めさせない。
- マイクの声（-40 dB より大きい 20 ms の合計）が `CIEL_INTERRUPT_SECONDS` 秒たまったら止める。たまらないまま話し終えたら止めず、その発言には返事もしない（`turns.py`）。発言は会話には残る。
- 会話モデルの側の `interrupt_response` は切る。止めるときは `session.interrupt()` で止める。
- LiveKit の中の作りが想定と違うとき（版を上げたときなど）は差し替えず、今までどおりにする（ログに警告）。
- 比べた案：会話モデルの側にすべて任せる（今のモデルでも話し始めで返事を取り消すので直らない）、GPT-Live（全二重で自然だが、シエルの声と人を覚える仕組みを失う）、話し始め・話し終わりの判定をすべて LiveKit に移す（いちばん賢いが、会話の進め方の作り直しが大きい）。

しきい値：0.6 秒では声の入った咳がすれすれ、0.8 秒では余裕があるが、本当の割り込みで止まるのがさらに遅れる。開発用でアプリから 2 回話してもらい、0.8 秒にした。

アプリでの確かめ（開発用、2026-10-22）：
- 1 回目（約 7.5 分）：「うん。」と 2 秒あけた「うんうん。」の声を足し合わせて止まった。直近 1.2 秒の声だけを数えるようにした（`WINDOW_SECONDS`）。そのあとの試験で、読点をはさんだ長い文が直近 1.2 秒では 0.8 秒に届かず、3 秒で打ち切られて「止めない・返事もしない」になることが分かった。話し始めてからの声の合計が 1.2 秒でも止めるようにし（`TOTAL_SECONDS`）、話し終わるまで打ち切らないようにした。
- 2 回目（約 3 分）：相づち（「うん。」「うんうん。」「へえ。」など）8 回はすべて止めず、本当の割り込み 3 回はすべて止めた。「話し始めた」の知らせから止めるまで 0.6〜1.7 秒（「うーん」のように間をあけて話し始めると遅い）。利用者の感想は「割り込みは少し遅いかも、でもこれぐらいがちょうどいいのかも」。
- 「それは知っている。」のような、シエルが話している間の短い文（声 0.78 秒）も相づちと同じに扱われ、返事をしない。声の量だけでは相づち（「うん。うんうん。」が 0.86 秒）と分けられない。話し終えてから文字起こしを見て返事をする案は、今は入れない（利用者の判断）。

2026-10-22 に本番にも入れた（既定 0.8 秒）。スマホのスピーカーでシエル自身の声をマイクが拾う場合（エコー除去が効かないとき）は、長く続く声として止まるので、この変更では直らない（確かめていない）。
