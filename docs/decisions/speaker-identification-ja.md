# 多人数の会話での話者の識別の決定記録

日付：2026-10-15（日本時間）、2026-10-16 更新（2 人のときも判定する、覚えている人は道具で調べる、返事を作らせるのを文字起こしの確定まで待つ、多人数では呼ばれたときだけ作らせる）。状態：試作。

## 声の登録の手順と、長めの同意の言葉（2026-10-25追加）

[調べたこと](../speaker-recognition-research-ja.md)の案 A・B。短い声では本人を確かめられないので、声の見本は「会話のついで」ではなく、決まった文を読んでもらって作る（Google・Amazon と同じやり方）。同意も画面ではっきり取る。

| 項目 | 決定 | 理由 |
|---|---|---|
| 入口 | 参加者パネルの札から「声を登録する」（まだ覚えていない人）・「声を登録し直す」（声を覚えている人。直前に確かに話したときだけ。この端末の声の見本を足す） | 名乗りや同意が声で通らなくても登録できる。持ち主が別の端末で使い始めるときにも、すぐ当たるようにできる |
| 同意 | 画面に、何を保存するか（名前・声の特徴。録音そのものではない）、お話も少し覚えること、「私の声を忘れて」でいつでも消せることを出し、本人が名前を入れて「同意して始める」を押す | 口の「いいよ」より、はっきりした同意になる（調べたこと 3） |
| 読む文 | 4 つ（`CielConversationUI.Enroll.cs`）。登録のことだけを言う文（「シエル、これから私の声を覚えてもらいます。」など） | 読んだ文がその人のメモの元にならないように。会話サーバーも、登録の読み上げはメモの元にしない（`Judgment.enroll`） |
| 受け付け方（`speakers.py` の `_enroll_judge`） | 1.2 秒以上の発言を読み上げとして受け付ける。これまでの読み上げ（すでに声を聞いている人なら、その声）と 0.35 未満なら「ほかの方の声」として受け付けない。1 つの文が息つぎで区切られたもの（前の読み上げから 1.2 秒以内）は、同じ文の続きとして数えない（声は見本に足す）。文の切れ端は知らせずに読み流す。180 秒で終わらなければやめる | 開発用の試験で、1 つの文が 2〜3 個に区切られ、3 つ目の文で登録が終わってしまった |
| 保存 | 4 つ読み終えたら、名前と声（読み上げた声すべて）を保存し、お話のメモの同意も記録する。同じ名前の覚えている人がいれば、声が近い（平均 0.35 以上）ときだけその人に足し、違えば「同じ名前の方がいます」 | 別の人が名前を名乗って、覚えている人に声を足せないように |
| 登録の途中 | シエルは返事をしない（`turns.py`）・自分から話しかけない（`initiative.py` の `paused`）。読み終えたら、話し終わるのを待って、名前を呼んでお礼を言う（`enroll_done.md`。名前は `{name}` で本文に入れる） | 読み上げに答えたり、読んでいる途中に話し始めたりしないように |
| アプリとのやりとり | アプリ → `ciel.speakers` の `enroll_start`（`speaker_id`・`name`）・`enroll_cancel`。会話サーバー → `ciel.event` の `enroll.state`（`active`・`accepted`・`needed`・`status`）。始められなかったときも、わけを `status` で返す | 画面に次の文・やり直し・結果を出す |
| 長めの同意の言葉（案 B） | シエルが覚えてよいか聞くとき、「『シエル、ハカセの名前と声を覚えていいよ』のように、お名前を入れて答えてください」と添える（`speakers.md`）。短い「いいよ」でもそのまま進める。何人かいて声の確認がうまくいかないときは、「声を登録する」があることを一度だけ伝える | 長い答えなら、声でも本人だと確かめられる |

確かめたこと：自動テスト `tests/test_speaker_enroll.py`（新しい人の登録と同意の記録、読み上げの印・切れ端・ほかの人の声、息つぎで区切られた文、やめる、断る場合、覚えている人の声を足す条件、同じ名前の人）と、登録の途中は返事をしないこと（`tests/test_turn_context.py`）。回帰テスト 259 件。Unity の `CielPlayModeShot` の `people` で、同意の画面と読み上げの画面（2 / 4、ほかの方の声）を撮った。開発用の会話サーバーで、読み上げの声で 4 つの文を読み（1 つは 2 個に区切られた）、4 つとも受け付けて保存し、その後の発言が覚えている人として当たった（0.63）。読み上げの途中にシエルは話さず、読み終えたあとに「ありがとう、テスト花子さん！これで、次からはあなたの声で分かるようになるのですね」と言った（試験用の人は削除した）。
まだ：実機のアプリ・実際の人の声での登録。登録のあと、別の日の最初の発言から当たるか。

## 短い名乗り・返事で同意が受け付けられない件（2026-10-25追加）

利用者の声（2026-10-25）：複数人で使うと、何度も同意を求められて、なかなか覚えてくれない。自己紹介や「いいよ」が短いので、本人の声として使われていないのでは。

原因：声のある部分が 1.0 秒未満の発言は、声の特徴を計算せず「不明」にしていた。ふたりきりでなければ、「不明」の発言で今話している人の情報が消える。名前の確認・保存は「今話している人を確かに当てていること」が条件なので、短い名乗り・「いいよ」のたびに「もう少し長めに名乗って」「覚えていい？」がくり返された。本番のログでも、0.1〜0.9 秒の発言がたびたび捨てられていた。

| 項目 | 決定 | 理由 |
|---|---|---|
| 人を決める長さ | 1.0 秒 → 0.8 秒（`CIEL_SPK_MIN_SECONDS`） | 「私は田中です」は無音を除くと 1 秒に届かないことがある |
| 短い返事（0.3〜0.8 秒） | 声の特徴を取り、30 秒以内に話した直前の人（`recent`。間に短い物音の「不明」が入っても残す）の返事とみなし、直前の判定の確かさを引き継ぐ（`_judge_short`）。ほかの人の声だとはっきり分かるとき（0.35 以上で、直前の人より 0.05 以上近い）だけ「不明」。新しい人は作らず、見本にも足さない | 名乗った人に「覚えていい？」と聞いた直後の「いいよ」を、その人の同意として受け付けるため |
| 声で本人を確かめない理由 | 会話サーバーで流した短い声（0.4〜0.7 秒）は、同じ声どうしでも 0.18〜0.26 にしかならず、ほかの人（0.17〜0.29）と区別できなかった（読み上げの声を 1 回で作り、間で切り分けて流した） | 声で確かめる決まりにすると、本人の「いいよ」も断ってしまう |
| 短い名乗りには名前を付けない | 短い発言で直前の人とみなしただけのときは、まだ誰にも結び付けていない名前を付けない（`last_short`。`_confirm_name`・`_name` は「確認待ち」を返す）。すでにその人に結び付けた名前への「いいよ」は受け付ける（2026-10-25 追加） | 名前を知らない人Aが話した直後に、別の人が初めて短く「田中です」と名乗ると、A に「田中」を付けてしまうため。名乗った人がもう少し話せば、その人に結び付く |
| 残る危うさ | 直前の人の代わりに別の人が短く「いいよ」と答え、その声がだれの声とも分からないときは、直前の人の同意として受け付けてしまう | 同意は、シエルが本人に名前で聞いた直後の返事に限られる。はっきりほかの人の声なら断る。気になる場合は `CIEL_SPK_SHORT_SECONDS` を上げると、短い返事を使わない（以前のふるまい） |

確かめたこと：自動テスト `tests/test_speaker_short.py`（直前の人の返事として確かさを引き継ぐ、ほかの人の声なら不明、短い物音を挟んでも直前の人を残す、30 秒を過ぎたら返事とみなさない、「たぶん」は「たぶん」のまま、0.8 秒なら新しい人、短い「いいよ」で名前と声を保存できる）と回帰テスト 250 件。開発用の会話サーバーで、読み上げの 2 人（男性・女性）を流し、短い「いいよ」2 回が直前の人の返事とみなされ、ほかの人の声に近い短い発言は不明になったことをログで確かめた。
まだ：読み上げの声は、同じ人の 1〜2 秒の発言どうしでも 0.30 前後で別の人に分かれ、シエルが同意を聞く前に「いいよ」を流してしまったため、名乗り→同意→保存の一連の流れは確かめられていない。実際の人の声で確かめる。
### 短い声の類似度が低い原因の調査（2026-10-25）

会話サーバーの処理（声を取り出す区間・前に足す 0.8 秒・声の部分だけにする処理）で、声が崩れていないかを調べた。

- 調べ方：判定ごとの数字（区間・声の長さ・全員との類似度・結果）をデバッグ用の会話ログに `speaker_judgment` として残すようにした。試験用の会話サーバーでは、`data/debug/AUDIO` のファイルがある間だけ、判定に使った声（取り出した区間と、声の部分だけにしたもの）を WAV で残す（`debug_log.save_audio`。実際の人の声が残るので、調べ終えたら消す。本番では使わない）。読み上げの 2 人を流し、送った音声と、会話サーバーが取り出した声を ECAPA で比べた。
- 分かったこと：
  - 送った音声と取り出した声は 0.86〜0.92（1 つは 0.65）で一致した。区間の取り方・時刻・サンプリング周波数に問題は無く、LiveKit を通っても声は崩れていない。
  - 同じ読み上げの声でも、別の発言どうしは 0.1〜0.5 にしかならなかった（同じ 1 回の読み上げから切り分けた、名乗り と「いいよ」で 0.21〜0.30）。読み上げの声は、文ごとに声の特徴が大きく変わる。実際の人の声は、本番のログで端末の持ち主の短めの発言が 0.48〜0.74 だった。
  - 読み上げの声では、基準の値（`SHORT_MATCH` など）を決められない。実際の人の声で測る必要がある。
- 訂正：以前ここに書いた「手元で計算した読み上げの短い声は、同じ声で 0.50〜0.59」は、試験の参加者の音声（48 kHz）を 16 kHz として計算した誤りだったので消した。

あわせて：会話の始めのあいさつ（`greeting.md`）が、指示の言葉（「朝ならおはよう、夜ならこんばんは、時間帯に合わせて…」）を読み上げたことがあったので、書き方を直した。

## 端末の持ち主と、人違いからの回復（2026-10-24追加）

利用者の声（2026-10-24）：アプリを起動してから、かなり話しかけてようやく思い出してもらえる。一度誤って「知らない人」になると、思い出してもらうのがほぼ不可能。会議で初めて会う人には向いているが、毎日使う人をもっと早く確実に認識してほしい。ログイン機能とのハイブリッドも案に出た。

原因：`_judge` は、この会話で聞いた人を覚えている人より優先する（`s_score >= k_score`）。一度「知らない人A」が作られると、その人の新しい声（同じマイク・同じ部屋）は、前に別の経路で録った見本より A のほうに近くなり、ずっと A のままになる。最初の数回は、端末のマイク経由の声が覚えている見本と 0.35〜0.5 くらいにしかならず、「知らない人」になりやすい。

| 項目 | 決定 | 理由 |
|---|---|---|
| ログインにしない | アカウントやパスワードは作らない。代わりに、端末を持ち主（声を覚えている人）に結び付ける | 声で本人を確かめる今の作りを残したまま、「この端末ならたぶんこの人」という手がかりだけを足せる。ログインは、会議でほかの人が話すときの判定には役立たず、入力の手間も増える |
| 結び付け方 | アプリが端末の中で、端末 ID（16 バイト）と合言葉（32 バイト）を乱数で作って持つ（PlayerPrefs）。つないだとき・会話サーバーが入ってきたときに `hello` を送る。持ち主にするのは、参加者パネルの「〇〇さんをこの端末の持ち主にする」（直前に話した人を「確か」に当てた、声を覚えている人だけ）。「持ち主をやめる」もパネルから | 本人がその場で話していることを、声の判定で確かめてから結び付ける。合言葉が合わないと持ち主にならない・やめられない |
| 保存するもの | 新しい表 `device_owners`（端末 ID、合言葉の SHA-256、人の番号）。人を消すと一緒に消える。合言葉そのものは置かない。比べるときは時間の差が出ない比べ方（`hmac.compare_digest`） | 仕様書 8 章（最小限の保存）。DB を読めても合言葉は分からない |
| 持ち主を優先して当てる | その場にいる人が「ひとり」「身近な人」のときだけ。持ち主の見本に 0.30 以上（`CIEL_SPK_OWNER_MAYBE`）で、ほかの人（この会話の人・ほかの覚えている人）より 0.10 低いまでなら「たぶん持ち主」にし、知らない人を作らない。「確か」は 0.50 以上（`CIEL_SPK_OWNER_SURE`）で、ほかの人より 0.05 以上近いとき。人違いだと言われて分けた人がよく当たるとき・その会話で持ち主が人違いだと言われたあとは、優先しない | ひとりのときは、ほぼ持ち主が話している。「確か」はメモを渡す元になるので、家族など似た声の人を取り違えないよう高めに残す。「人前」（会議）では優先しない |
| 経路ごとの見本 | 見本（`voiceprints`）に経路の印 `channel` を付ける（端末 ID の SHA-256 の頭 16 文字。端末 ID そのものは置かない）。持ち主として「確か」に当たった 2 秒以上の声は、0.50 以上なら 1 会話に 6 つまで見本に足す（ほかの人は今までどおり 0.60 以上・3 つまで）。1 人・1 経路の見本は 20 まで、1 人の合計は 60 まで（以前は 30） | マイクや経路が変わると声の特徴も変わる。その端末で録った見本が増えると、次の会話から最初の発言で当たる。1 つの経路の見本が、ほかの経路（最初に覚えたときの見本など）を押し出さないようにする |
| 人違いからの回復 | この会話の知らない人（名前を付けていない・分けた人ではない）の声が 3 回以上たまったら、最近 5 回分の類似度の平均を覚えている人と比べる。0.50 以上（`CIEL_SPK_RECOVER`。ひとり・身近な人のときの持ち主は 0.42）で、次の人より 0.05 以上近ければ、その人にまとめる（発言の記録もまとめた先にする）。会議（人前）で、その人がこの会話ですでに別に話しているなら、まとめない | 1 回分より、何回分かまとめたほうが確か。会議では似た声の別の人をまとめてしまわないように |
| 手でまとめたとき | 参加者パネルで、知らない人を声を覚えている人に「同じ人」とまとめたら、その知らない人の最近の声を 3 つまで、覚えている人の見本に足す（経路の印付き）。以前は、この会話の間だけだった | アプリの利用者が直したのに、次の会話でまた知らない人になるのを防ぐ。足すのは 3 つだけで、その人の見本全体は変わりすぎない |

アプリの表示：持ち主の札には家の印（`Icons/home.png`、`scripts/ui/make_ui_sprites.py`）を付ける。パネルでは「この端末の持ち主です」と、持ち主にする・やめるボタンを出す。`speakers.state` に `owner`（この会話での持ち主の札）・`owner_name`・`pairable`（持ち主にできる人）を足した。

確かめたこと：自動テスト `tests/test_speaker_owner.py`（15 件。持ち主にする・やめる・合言葉違い・おかしなメッセージ、ひとりのときの「たぶん持ち主」、人前では優先しない、ほかの覚えている人と同じくらい近いときは「確か」にしない、分けた人は持ち主にしない、持ち主の見本の足し方と経路の印、知らない人からの回復と回復しない場合、手でまとめたときの保存）と通常の回帰テスト 233 件が合格。使い捨ての PostgreSQL（pgvector 0.8.0-pg17、自宅サーバーで一時的に起動して削除）で結合テスト 7 件（持ち主の表、人を消すと持ち主も消える、経路ごとの見本の上限を含む）が合格。開発用の会話サーバーへ反映し、開発用の DB に表と列ができたことを確かめた。Unity では `CielPlayModeShot` の `people` で、持ち主の札の印とパネルを撮って確かめた。
まだ：実際の端末・声で、持ち主にしたあと最初の発言から当たるようになるか、「たぶん持ち主」の 0.30 が低すぎないか（家族が同じ端末で話したとき）。

### 持ち主の名前を呼んであいさつする（2026-10-25追加）

利用者の希望：アプリを開いたときのあいさつの時点で、端末の持ち主が分かっていて、名前を呼んであいさつしてほしい。

| 項目 | 決定 | 理由 |
|---|---|---|
| あいさつの中身 | ひとり・身近な人のときに持ち主が分かれば、`greeting_owner.md` の指示であいさつする。名前を最初に呼び、前に話した日に合わせ、覚えていること（最近の 5 つ。同意があり、忘れる依頼の処理中でないもの）から 1 つを気にかけて聞く。シエルとの関係（`relationship.context`）も口調の下敷きに添える。人前のとき・持ち主がいないときは、今までのあいさつ | 声で確かめる前でも、ひとりのときに端末を開くのはほぼ持ち主。「たぶん」として渡し、別の人の声で返事が来たら合わせる。人前では、ほかの人に覚えていることが伝わるので使わない |
| 名前の渡し方 | 指示の文に名前を差し込む（`{name}`） | 名前を別の行のデータとして渡すだけでは、「あなた」とあいさつすることがあった |
| 持ち主が分かるのを待つ | あいさつの前に、アプリの hello を最大 2.5 秒待つ（`CIEL_OWNER_WAIT`）。会話サーバーは受け取りの準備ができたら `device.hello_request` を送り、アプリは会話のしかた・声の大きさ・hello を送り直す。受け口（`data_received`）は `session.start` の前に作る | アプリが会話サーバーの入った瞬間に送った知らせは、届かないことがあった（開発用の試験で 3 回に 2 回、hello か会話のしかたが落ちた）。古いアプリは送り直さないので、待ちすぎない |
| 道具 | あいさつでは道具を使わせない（`tool_choice='none'`） | まだ誰も話していないのに話者の状態を調べ、「声の登録がまだ」と話したことがあった |

確かめたこと（開発用の会話サーバー、試験用の人「テスト太郎」を作り、終わったら削除）：アプリと同じ知らせを送る試験の参加者で、ひとり・身近な人の 5 回とも「テスト太郎さん、こんにちは！」のように名前を呼び、覚えていること（来週のフルマラソン・山の写真）を 1 つ聞いた。人前の 1 回は今までのあいさつ。hello を送り直してもらうようにしてからは、hello が落ちなかった。自動テスト（あいさつに添える中身・人前では空・同意や忘れる依頼の処理中は覚えていることを渡さない）を足し、回帰テスト 237 件が合格。
まだ：実機のアプリ（送り直しの対応はアプリの更新が要る）で確かめていない。

## アプリの参加者パネル（2026-10-23追加）

シエルが今だれがいると思っているかを、会話の画面で見えるようにし、その場で直せるようにした（利用者の希望、2026-10-23）。

| 項目 | 決定 | 理由 |

## 会議の仮名簿と本人確認（2026-10-18追加）

会議で本人の自己紹介・第三者からの紹介の両方が登録できない報告があった。直近ログでは、21:03台に `no_speaker` で2回、21:04台に `identity_uncertain` で2回の名前登録拒否を確認した。直前の声が0.4〜0.8秒、または本人判定が不確かなためであり、この会話に保存エラーの記録はなかった。前段の声の判定が不確かでも名前を受け付けるため、名前の仮受付・本人との対応確認・本人同意後の保存を分けた。

- `register_participant_name(name, self_introduction=false)`：他者紹介の名前を今の接続だけの名簿で受け付ける。紹介者の名前や声は変更しない。本人の自己紹介では `self_introduction=true`。短い声・話者不明でも仮受付IDを返し、声との対応が未確認の `pending_identity` とする。
- `confirm_participant_name(registration_id, confirmed_name, remember=false)`：本人が名乗った名前と、確かに識別された現在の話者を照合する。確認できたら `session_named`。本人の明示同意を得て `remember=true` にした場合だけ既存のトランザクションによる永続保存へ進む。保存に失敗しても、確認済みの会話中の対応は残す。確認前の同意を後から別の声へ適用しない。
- `people_here`：仮受付ID・名前・対応状態の `registrations` と、実際に声を聞いた `heard_speakers` を分けて返す。名簿は最大64件で、上限では `registration_limit` を返す。同名候補が複数なら推測で統合せず、IDを確認する。別の接続へは持ち越さない。

紹介者自身による確認、別の話者からの確認、既存の呼び名との衝突、不確かな本人判定は保存を進めない。改名・声を忘れる操作では名簿の対応状態も更新する。既存の `name_speaker(remember=false)` も、話者不明・不確かな場合は名前の仮受付を残す。

実モデルの合成会話で、第三者紹介を本人の訂正と混同して `not_this_speaker` を呼ぶ、第三者紹介を `self_introduction=true` とする挙動が出た。指示の修正に加え、ハーネスが返答の元発言を保持し、ツールが実際の書き起こしを最大1秒待って照合する処理を追加した。明示的な他者紹介は自己紹介の引数を補正し、本人の訂正を確認できない場合の話者分け直しは拒否する。元発言が取れない・本人の名乗りを確認できない場合は、名前を仮受付したままにする。判定基準を下げたり、前の人の声を推測で使ったりはしない。照合は日本語の保守的な表現照合のため、名前の表記ゆれや未対応の言い方では再確認が必要になる。

## 名前の登録・保存確認の見直し（2026-10-18）

自己紹介と「名前を覚えた？」への返答が曖昧という報告を受け、名前の設定と保存確認を見直した。今回の実会話でどの経路が起きたかは未確定だが、コード上では以下の問題があった。

## 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| 方式 | 会話モデル（Realtime API）には今までどおり声を渡し、発言が終わるたびに（2 人でも多人数でも）会話サーバーで話者を判定して、「[発言者：…]」の 1 行を足してから返事を作らせる | Realtime API に話者の機能は無い（開発者フォーラムに要望が出ている段階）。声を文字にしてから渡す方式（話者分離つきの文字起こし）より、抑揚が伝わり、遅れと料金が増えない |

## 仕様書 8 章との関係

仕様書 8 章は「初期版ではユーザー音声と会話全文を自前の永続ログへ保存しない」。この方式は録音も会話も保存しない。保存するのは、**同意した人の名前と声の特徴（192 個の数）と日時だけ**。声の特徴も個人を識別できる情報なので、次のように扱う：

- 同意した人だけ保存し、本人の依頼で消す。
- DB は自宅サーバーの中だけ（外から入る口を開けない）。パスワードは `server/.env`（Git に入れない）。
- ログには名前も声の特徴も出さない（DB の番号と類似度だけ）。
- ほかの人へ公開する前に、利用規約・説明の文面と、保存の期間（例：長く会っていない人は消す）を決める。

## 人違いを直す（2026-10-16）

- 声が似ていて別の人と判定されたら、本人が「私はハカセじゃない」と言い、会話モデルが `not_this_speaker` を呼ぶ。

  1. 発言の声が会話に入る（`input_audio_buffer.committed`）前に「[発言者：…]」と `response.create` が送られ、返事が 1 つ前の発言に答えた。

## 判定を 1 つにまとめ、「たぶん」を増やした（2026-10-18）

- 利用者の試験（ハカセさんと、もう一人の 2 人で会話）のログで、次の 2 つが起きた。
  - もう一人の方の最初の発言が、ハカセさんに 0.47 で「確か」になった。そのときは、もう一人の声をまだ一度も聞いていなかったので、比べる相手がいなかった（次点との差 1.47）。
  - もう一人の方の声が一度だけ 0.42 になり、「知らない人B」が作られて、シエルが「3 人いる」と答えた（声が遠い・はっきりしないとき）。
- あわせて、シエルへの「[発言者：…]」（返事を作るとき）と、記録係・議事録の話者（文字起こしのとき）を、別々に計算していたので、同じ発言でも食い違うことがあった。
- 決めたこと（利用者の判断）：
  - **判定を 1 つにまとめる**：会話モデルの側が区切った発言ごとに、話し終わったらすぐ、その声で 1 回だけ判定する（`speakers.py` の `judge`、`turns.py` の `_judge`）。返事を作らせるときは、その返事に含まれる区間のうち、話者が分かった一番新しい区間の判定を使う。文字起こしは、組になる区間の判定を使う。記録係・議事録には、シエルと同じ言葉（「ハカセ」「たぶんハカセ」「知らない人A」「不明」）で渡す。
  - **覚えている人の「確か」を 0.55 に上げる**（`CIEL_SPK_SURE`）。本人はこの日 0.60〜0.88 だった。0.35〜0.55 は「たぶん」。
  - **この会話で聞いた人にも「たぶん」を作る**：0.35〜0.45 は、新しい人を作らず「たぶん知らない人A」にする。「たぶん」の声は見本に足さない。
  - 「たぶん」と「不明」の発言は、メモ・シエルの気持ちの元にしない。大事そうなことを「たぶん」の人が言ったときに聞き返す仕組みは、様子を見て決める。
- 確かめた（自宅サーバー、本番とは別のコンテナ。試験用の人は削除）：
  - 類似度を決めて作った声の特徴で：0.47 →「たぶん覚えている人」、0.62 →「確か」、知らない人A に 0.42 →「たぶん知らない人A」（B を作らない・見本に足さない）、0.55 → 知らない人A。
  - 読み上げで作った 2 人の声（男性・女の子。女の子は小さめの音量で、声の高さも 1.25 倍）を交互に 5 発言：5 発言とも、シエルへの [発言者] と記録係の話者が同じだった。女の子は 3 発言とも「知らない人A」1 人にまとまり（類似度 0.54 など）、短い「うん。」は両方とも「不明」。メモには男性の「ミルクティー」だけが残り、女の子の美術館・上海歌舞団の話は残らなかった。
- まだ：実際の人の声で、0.55 がハカセさん本人を「たぶん」にしすぎないか（本人の 0.60 台の発言はあまり余裕がない）。
