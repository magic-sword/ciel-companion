# 操作とイベント入力を持つサービス境界

決定日：2026-11-10。状態：採用、標準pipeline向けの初版を実装済み。実機と本番反映は未確認。対象：シエルのサービス入力とリアクション。

## 背景

実装前の背景：能力カタログとMCP処理の整理によって、LLMと基盤からサービスを呼ぶ経路を揃えた。一方、接触・ゲームの被ダメージ・配信コメント・歌の変化への反応は、各機能の受信・待機・通知処理に分散している。

Mouthは発話の入口として使われているが、即時表情、入力の有効期限、異なる機能間の優先順位を管理する共通契約はない。また、操作ごとに閉じるMCP接続は、後続の継続通知を受け取る入口にはならない。

## 決定

1. サービス境界に操作の依頼・結果と、非同期イベント入力を設ける。継続受信のライフサイクルは会話・接続単位で管理する。
2. 道具の段階的ロードとイベント受信を独立にする。観測事実の受信によって操作権限を増やさない。
3. イベントを会話単位の有界キューとコードの規則で調停し、即時表情・会話への補足・発話へ振り分ける。既存Mouthを使い、入力の分類用LLMを追加しない。
4. 正式な状態の反映と、期限付きのリアクションを区別する。発話の省略や混雑で作業結果・取消確認を失わない。
5. 既存通信と即時反応を活かし、機能ごとに直接通知経路を共通調停へ移す。入力をMCPのプッシュ通知に全面変更することや、別プロセス化は今回の設計の前提にしない。

## 実装への影響

イベントの識別・世代・順序・期限と、表情と発話それぞれの反応済み情報が必要になる。Unityの即時反応と後続のLLM反応には対応IDと表情の優先規則を設ける。コメントなど外部テキストの権限を発話と道具の続きまで維持する。

詳細と受け入れ条件は[サービス入力とリアクションの設計](../service-events-and-reactions-ja.md)。採用方針の入口は[設計方針の正本](../design-policy-ja.md)。既存の単体・DB・能力ロードの確認結果を、この共通入力基盤の検証結果として流用しない。

実装と検証は[共通反応基盤の導入記録](../reactions-runtime-2026-11-10-ja.md)を参照。
