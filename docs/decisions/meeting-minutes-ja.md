2026-10-18更新：発言の収集・保持・議事録の処理位置は[共通会話履歴](conversation-history-ja.md)へ移した。以下の「要約後に元発言を捨てる」は導入当初の方式。現在は共通履歴の保持上限まで会話検索にも利用できる。

日付：2026-10-16（日本時間）。状態：試作（段階 B）。話者の識別（[決定記録](speaker-identification-ja.md)）と、会話の裏で文字のモデルに書かせる形（[メモの決定記録](person-notes-ja.md)）の上に作る。

## 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| 何をするか | シエルを含む会議の発言を、議事録（概要・話したこと・決まったこと・宿題・決まっていないこと）にまとめ、Discord で共有できるようにする | 利用者の希望（2026-10-16）。LINE は当面やらない（下の「LINE について」） |
| いつ記録するか | 「始め」と「終わり」をはっきり知らせたあいだだけ。常に記録することはしない | 会議の参加者に、記録していることが分かるように |
| 知らせ方 | 始めと終わりは 3 つの口から（段階 B、2026-10-16）。(1) アプリの「議事録」のボタンと (2) 管理用のコマンド `minutes_admin.py` は、LiveKit のデータのメッセージ（topic `ciel.minutes`、`{"v":1,"type":"minutes.control","action":"start"|"finish"}`）を会話サーバーへ送る。(3) 声で頼まれたら、会話モデルが道具 `start_minutes`・`finish_minutes`（`tools/minutes.py`）を呼ぶ。道具はすぐ戻り、返事を作り直さない（`reply_required=False`） | 会議の中で、手を止めずに頼めるように。アプリが使えないときのために管理用のコマンドも残す |
| 始めた・終えたときの一言 | どの口から始めても、議事録係（`minutes.py` の `on_change`）の知らせを受けて、会話サーバーが「[議事録：とり始めた]」などの 1 行を添えて返事を作らせ、シエルが一言告げる（多人数でも黙らない）。言い方は `config/prompts/minutes_voice.md`。道具を呼ぶときは何も言わせない | 参加者に、記録を始めた・終えたことが分かるように。道具のあとに返事を作らせる形だと、ボタンから始めたときと言い方が変わり、二重に話すこともある。`generate_reply(instructions=…)` は会話の指示の後ろに足される（LiveKit の OpenAI Realtime の実装で確かめた）ので、人物像は保たれる |
| アプリの表示 | 会話サーバーが、変わるたびに `ciel.event` で `{"v":1,"type":"minutes.state","recording":true|false}` を送る。アプリのボタンは「議事録（タップで始める）」と「議事録をとっています（タップでまとめる）」を切り替える。接続のたびに「とっていない」に戻す | 会話サーバーは部屋ごとに新しく入るので、接続したときはいつもとっていない |
| 記録の中身 | 発言ごとに「時刻・話者・文」。メモリーの中だけにためる。話者は話者の識別の判定。あとで名乗った人は、その名前に直して渡す。名前の無い人は「参加者A」、判定できない発言は「参加者（不明）」。シエルの発言も入れる（感情の印と `[silent]` は外す） | 議事録に要る分だけ。DB には残さない |
| 誰がまとめるか | 会話の裏の別の文字のモデル（既定 `gpt-5.4`、`CIEL_MINUTES_MODEL`、reasoning は medium）。指示は `config/prompts/minutes.md`、出力は JSON で、Markdown にするのは `minutes.py` | 1 回だけの処理で質が大事なので、メモの `gpt-5.4-mini` より強いモデルにした。形を JSON に決めておくと、Discord 以外へも出しやすい |
| 長い会議 | とっているあいだ、10 分ごと（`CIEL_MINUTES_ROLL_SECONDS`、既定 600）に、それまでの議事録（`previous`）とその後の発言を渡して作り直し、まとめた発言は捨てる。終わりには残りの発言だけを合わせる。作れなかったときは発言を残して次に回す。終わりのまとめにも失敗したら、途中までの議事録に「まとめきれなかった発言」をそのまま付ける | 終わってから下書きが届くまでの待ち時間を短くし、文字のモデルに渡す量が増えすぎないように。メモリーにためる発言も減る |
| 聞き間違い | 「シエル」が「CL」などになることを指示で教え、直させる。意味の分からない言葉は書かせない | 文字起こしの癖（[メモの決定記録](person-notes-ja.md) の「シエルの聞き間違い」） |
| どこへ出すか | 利用者だけが見る Discord のチャンネルへ、Webhook（`CIEL_MINUTES_DISCORD_WEBHOOK`）で**下書き**として送る。共有先へは、利用者が確かめてから流す | 聞き間違いや、外に出したくない発言が混ざることがある。自動で共有先へは出さない |
| Discord の送り方 | 本文が 2000 字までなら本文で、長ければ頭だけ書いて全文を `.md` で添付する。名前は「シエル」、メンション（@everyone など）はすべて無効 | Discord の本文の上限。議事録の中の言葉で通知が飛ばないように |
| 送れなかったとき | Webhook が無い・失敗したときだけ、下書きを自宅サーバーの `server/agent/data/minutes/` に保存する（Git・デプロイの外） | 会議の議事録をなくさないため |
| 会話が切れたとき | とっている途中で会話が終わったら、そこまでで議事録にする | 「終わり」を送り忘れても残るように |
| ログ | 行数・文字数・送れたかだけ。会話も議事録の中身も出さない | 仕様書 8 章 |

## 使い方

1. Discord で、利用者だけが見るチャンネルを作り、「チャンネルの編集 → 連携サービス → ウェブフック」で URL を作る。
2. 自宅サーバーの `server/agent/.env` に `CIEL_MINUTES_DISCORD_WEBHOOK=<URL>` を書き、会話サーバーを起動し直す（`docker compose up -d agent`）。
3. 会議の参加者に、シエルが議事録をとることを伝える。
4. 始める：アプリの「議事録」のボタン（マイクボタンの左）を押すか、「シエル、議事録とって」と頼む。シエルが一言告げ、ボタンが「議事録をとっています」になる。
5. 終える：もう一度ボタンを押すか、「シエル、議事録まとめて」と頼む。少しあとに下書きが Discord に届く。
6. アプリを使えないときは、自宅サーバーの `~/work/ciel-companion/server` で：
   ```sh
   docker compose exec agent python minutes_admin.py start     # とり始める
   docker compose exec agent python minutes_admin.py finish    # まとめて、下書きを Discord へ送る
   ```
   シエルがいる部屋が 2 つ以上あるときは、`rooms` で一覧を見て、部屋の名前を付ける。
7. Discord の下書きを確かめ、直してから共有先のチャンネルへ貼る。
8. `data/minutes/` に保存されたときは、中身を確かめたあと `docker compose exec agent sh -c 'rm /app/data/minutes/*.md'` で消す（ファイルはコンテナの root が作るので、ホストからは消せない）。

## 確かめたこと・まだのこと

- 確かめた（自宅サーバー、実際の文字のモデル、2026-10-16）：
  - 博士・知らない人A（あとで田中と名乗る）・シエルの 8 行から、要約に約 10 秒。話題・決まったこと・宿題（担当、期限の「来週の水曜」→ 2026-10-21（水））・決まっていないことに分かれた。文字起こしの「CL」は「シエル」に直った。あいさつと「聞こえてますか」は書かれなかった。始める前の発言と `[silent]` は入らなかった。
  - Discord の Webhook の形（偽のサーバー）：短いと JSON の本文、長いと `files[0]` の添付。メンションは無効。
  - Webhook が無いとき・発言が少ないとき・とっている途中で会話が終わったときの動き。
  - 実際の部屋（試験用の参加者が合成した声で 4 文を話し、多人数のモード）：`minutes_admin.py start/finish` が会話サーバーに届き、5 行から議事録ができて `data/minutes/` に保存された（試験のファイルは削除した）。参加者の欄に、話していないシエルが入ったので、指示を直した（直したあとの確認はまだ）。
- 段階 B（2026-10-16）：
  - 長い会議（コンテナの中、実際の文字のモデル、間隔を 3 秒にして）：前半 4 行から途中の議事録が約 10 秒でできて、発言は捨てられた。後半で「三分→五分に決め直す」「モニターは借りられた」と話すと、終わりのまとめ（約 11 秒）で決め直しが反映され、終わった宿題は消えた。途中の議事録だけで残りが無いとき・終わりのまとめに失敗したときの下書きの形。
  - 実際の部屋（試験用の参加者が合成した声で話し、多人数のモード）：「シエル、議事録をとってくれる？」で道具が呼ばれ、シエルが「了解です、議事録の準備を始めますね」と告げ、アプリへ `minutes.state`（とっている）が届いた。アプリと同じ `ciel.minutes` のメッセージでも始め・終わりができ、終わりの一言と `minutes.state`（とっていない）が届いた。9 行から議事録ができ、Discord へ送れた（このとき `.env` に Webhook が入っていて、試験の下書きが 1 件届いた）。
  - 同じ試験で分かったこと：とっているあいだ、多人数なのにシエルが呼ばれていない発言にも返事をした（段階 A の試験では黙っていた）。「議事録をまとめて」に、すぐ道具を呼ばず「続けて聞いてるよ」と返し、次の返事で呼んだ。`minutes_voice.md` に「とっているあいだも答え方はいつもどおり（相づちを打たない）」「まとめてと頼まれたらすぐ呼ぶ」を足した。
  - 直したあとの試験（同じ形）：直らなかった。議事録をとらずに試しても、多人数のモードで呼ばれていない発言に返事をし、返事が 1 つ前の発言に答える形にずれた（議事録の指示を 1 行にしても同じ）。どの発言の前にも 0.5 秒くらいの「話者：不明」の区切りが入り、返事を作らせる回数が増えているのが一因と考えられる。段階 A のコードで同じ試験をして比べることは、本番の会話サーバーを戻す必要があり、していない。合成した声での試験に特有のことかもしれない（実際の会議ではまだ試していない）。
  - 直した（2026-10-16）：議事録の追加の前のコードでも同じようにずれ、議事録とは関係なかった。原因は、返事を作らせる時を LiveKit の手元の VAD の区切りで決めていて、発言の声が会話に入る前に作らせていたこと。文字起こしの確定まで待ち、多人数では呼ばれたときだけ作らせるようにした。同じ形の試験で、呼ばれていない 6 文には返事を作らせず、呼ばれた 2 文にはその発言について答えた。詳しくは[話者の識別の決定記録](speaker-identification-ja.md)の「返事がずれた件」。
  - 声で「まとめて」と頼むと、`finish_minutes` は次の返事で呼ばれた（すぐではない）。アプリのボタン・管理用のコマンドからは、すぐに始め・終わりができる。
  - Unity：バッチモードでコンパイルが通った（エラー 0）。ボタンの見た目と、実機・エディタでの押したときの動きは確かめていない。
- まだ：実際の会議（何人か・30 分以上）での要約の質と、話者の判定の間違いの影響。

## LINE について

LINE Notify は 2025 年 3 月に終わったので、LINE のグループへ自動で投稿するには Messaging API（公式アカウントのボットをグループに招待して push する）が要る。グループの ID を知るために外から届く受け口が一度は要り、無料の枠では push の通数がグループの人数の分だけ数えられる。利用者の判断（2026-10-16）で、当面は Discord だけにする。
